# AGENTS.md: .github

OnePeek's organisation-wide GitHub files: the shared CI workflows, the pull request template, the contributing and security guides, and the organisation profile. Every OnePeek repo uses these unless it has its own copy. This repo is public.

## Start here
- For any detail (what to build, how it behaves, names, data, limits), look in `onepeek-docs` first: the sibling folder `../onepeek-docs` or https://github.com/OnePeek/onepeek-docs. Begin with `standards/engineering-standards.md` and `standards/repo-map.md`, then grep and read only the files the task needs.
- If the docs are silent, unclear or disagree with these files, don't guess: ask, or open a docs pull request.

## Layout
- `.github/workflows/`: shared reusable workflows (`secret-scan`, `python-checks`, `node-checks`, `terraform-checks`, `release-tag`, `contract`, the contract between repos of decision 153, and `release-lock`, the release lock of foundation-playbook §5.4 for releases outside `release-ecs`/`operate`; since §5.4a one key per scope (`locks/{infra,backend,web,mcp}.json`, plus `locks/release.json` during the expand step), taken try-or-release, with a phase in each record that `finish` acts on, every wait capped by `scripts/check_lock_limits.py` against the runners' lifetimes) that every repo calls as `OnePeek/.github/.github/workflows/<name>.yml@<commit SHA>`. Every action is pinned to a commit SHA; downloaded tools are pinned and checksum-verified. Rules: `onepeek-docs/standards/branching-and-delivery.md`.
- **Supply chain (foundation-playbook §12a slice 4).** `osv-scan.yml` (every repo with a lockfile, on every pull request: Google's osv-scanner image pinned by digest; blocks on a scanner exit other than 0 or 1, on high or critical, or on any finding with a fix; waivers in the caller's `osv-scanner.toml` with `reason` and `ignoreUntil`; logic in `scripts/check_osv_results.py`); `ci-image-bump.yml` (weekly, caller-scheduled: moves digest-pinned CI container `image:` lines to their tag's current digest, failing on a pinned line it cannot move; pushes and opens a pull request only with the optional `CI_BUMP_APP_ID`/`CI_BUMP_APP_PRIVATE_KEY` App secrets (the onepeek-ci-bump App, docs PR #183); logic in `scripts/bump_ci_images.py`); workflow-lint rule 6 in `scripts/check_runner_labels.py` refuses a job `services:`/`container:` image that is not `image: <name>@sha256:<digest> # <tag>` on its own line (an exact `${{ inputs.* }}` or `${{ matrix.* }}` image passes: the caller pins it).
- **Runners.** Every reusable workflow takes `runner` (`onepeek`, `canary` or `github`, default `github`) and maps it, with the job's class, to `runs-on` itself; callers pass `runner: ${{ vars.RUNNER || 'github' }}` and never a label. Jobs that can hold a prod credential stay GitHub-hosted. `scripts/check_runner_labels.py` enforces the rules (`onepeek-docs` `architecture/lld/infra/ci-runners.md` §5.3-5.4); the prod-privileged job list is `.github/workflow-lint/github-only-jobs.yaml`.
- `actions/peer-ref` and `scripts/peer_ref.py` (delivery-pipelines §6.5): the one rule for which version of another repo a pull request is checked against (`dev`; `release` for a hotfix; the head of the repo's open `dev` → `release` pull request, else `release`, for a promotion). `contract.yml` runs the script from its `_shared` checkout at `${{ job.workflow_sha }}`; other callers use the action, pinned like a shared workflow (`uses: OnePeek/.github/actions/peer-ref@<sha> # vX.Y.Z`; `bump_pins.py` and `ship_change_set.py` move it with the workflow pins). Each check prints `peer: <repo>@<commit>` (always a commit) to its job log and summary; before a promotion merges, `ship_change_set.py` reads the line from the job log (`gh api repos/<repo>/actions/jobs/<id>/logs`), resolves the peer's release candidate again, passes when equal or when only the peer's own promotion merge commit (equal tree) differs, otherwise re-runs that check once and refuses if it still differs. `scripts/test_peer_ref.py` fails any workflow that computes a peer's ref itself.
- `PULL_REQUEST_TEMPLATE.md`: what changed, why, the docs link and how it was tested.
- `CONTRIBUTING.md` and `SECURITY.md`: how to contribute and how to report a vulnerability.
- `profile/`: the organisation's public profile page.
- `pins.yml` (every repo calls it): the repo's `OnePeek/.github` pins are all one `v*` tag's commit, and on pushes to `dev`/`release` and release pull requests `docs-version.txt` is on docs `main` (foundation-playbook §8a P2, S4; logic in `scripts/check_pins.py`). `depends-on.yml` (the first job of every pull-request workflow that runs on our runners, not only `checks.yml`; the others `needs:` it; callers trigger on `opened`, `reopened` and `synchronize`, never `edited`, and `ship_change_set.py` re-runs a dependent's checks when its dependency merges): fails with "waiting for <repo>#<n>" while a `Depends on: OnePeek/<repo>#<n>` line in the body names an unmerged pull request, and, with no line needed, when `docs-version.txt` names a commit not on docs `main` and in no open docs pull request. A pin that is a commit of an open docs pull request is the normal state of a change set, so `--check` only prints a notice ("waiting for onepeek-docs#N ... ship_change_set.py merges it first") and passes; `--strict` fails it, and `ship_change_set.py` and `preflight.py --release` apply that strict rule (calling `docs_waiting(strict=True)`), and `ship_change_set.py` merges docs first. `ship_change_set.py` also refreshes a code pull request whose only conflict with its base is `docs-version.txt` (merge the base, pin to the docs pull request head; `--refresh <repo>#<n>` does just that); the body is read live from the API with the job's `GITHUB_TOKEN` (`pull-requests: read`, granted by the caller's job), not from the event payload. Merging a docs pin push without a new CI run (`ship_change_set.py`) is only for a pin-only change on a base the green run tested; once required checks exist (GitHub Team, §5.7) that merge needs `--auto` or the wait (§8a P1, lessons L26 and L27). `spot-rerun.yml` (R1 of `ci-runners.md` §4; a repo's `spot-rerun-caller.yml` runs it on `workflow_run: completed` with conclusion failure for its CI workflows): when a failed job's log shows a spot reclaim and the run is on attempt 1, it re-runs the failed jobs once and writes the job names to the run summary (logic in `scripts/spot_rerun.py`). `package-cleanup.yml` (weekly, in each publishing repo): old `-next.*` and `0.0.0-pr<N>.*` npm versions go (§8a C3). Workflows that read other repos use the agents' App token (`AGENTS_APP_CLIENT_ID`/`AGENTS_APP_PRIVATE_KEY`, §8a S6); there is no fallback token (`ORG_READ_TOKEN` and `INFRA_READ_TOKEN` are retired).
- `workspace/`: the root setup for the folder holding all repos side by side, the shared Claude Code skills and agents (`skills/`, `agents/`, synced into each repo by `setup.py --sync-repos`), `packet.py` (a task packet for any repo at its pinned docs commit), `local_ci.py` (a repo's pull-request CI on the laptop), `preflight.py` (before every push and release: local CI, pins, tool versions, `--release` prerequisites; the `preflight` skill), `live_preflight.py` (onepeek-infra, `preflight.py --live`: read-only IAM simulation of a plan, changed images under their task memory limit, the edge's answer to the smoke User-Agent; §8a P9) and `ship_change_set.py`. `AGENTS.md` is the root instructions file for every tool (`CLAUDE.md` loads it for Claude Code); `setup.py` links every repo's Claude Code skills and agents into the root `.claude/` (run once after cloning, and again when a repo adds one; `--check` reports drift).

## Principles
- **Mirror the standards.** These files repeat `engineering-standards.md` in short form; when the standards change, these change with them.
- **Public by design.** Nothing here may hold a secret, an internal link or personal data.

These principles grow over time: when a review teaches us something, add it here in one line.

## Rules every OnePeek repo follows
Read `onepeek-docs/standards/engineering-standards.md` (https://github.com/OnePeek/onepeek-docs/blob/main/standards/engineering-standards.md) before changing anything. In short:
- **Names and language.** Canonical names from founder decision 97; plain English in anything a person reads; never name the prior internal product.
- **Pull requests.** Every change goes through a pull request; before launch, review is optional (decision 124). People and AI agents never commit, push, merge or deploy without an explicit instruction.
- **Repos pin the shared workflows by full commit SHA** with the version tag as a trailing comment (`@<sha> # v1.4.0`), never by a moving tag. `tag-main.yml` cuts a version tag on every merge here. Pins move by Dependabot pull request (proven in phase 2 of workstream W7); until then by `python3 scripts/bump_pins.py <repo-dir> <tag> <sha>`. Nobody edits a pin by hand.

## 8a. Hardening pass (2026-11-04)

Audit of 2026-11-04 (founder: cover everything except branch protection, which waits for GitHub Team, §5.7, and KMS key consolidation, which is a later design discussion). Values marked *provisional* are recommended defaults.

**Security and reliability**
- **S1, runner fleet changes from `release`:** the CI account's apply role (`ci-runners.yml` apply) trusts `ref:refs/heads/release` **and** `job_workflow_ref` = `OnePeek/onepeek-infra/.github/workflows/ci-runners.yml@refs/heads/release`, not `dev`. A push to `dev` can no longer change the machines (image, launch settings) that run preprod deploy jobs; the fleet changes through the same gate as a preprod deploy. Pull requests still plan it: the guard that skips the privileged plan when a pull request changes workflows is skipped only for a `dev` → `release` pull request, which carries only changes already reviewed and merged on `dev`, so it plans; any other pull request (into `dev`, or another branch into `release`) that changes workflows skips the privileged plan. A release pull request open longer than the plan artifact's retention (5 days) is re-planned (re-run its plan job) before merge; the apply refuses without a reviewed plan. The founder's `scripts/up ci bootstrap` (the trust move) runs before the first fleet change merges into `release`. Supersedes the `dev` apply of `ci-runners.md`. The `job_workflow_ref` part arrives with the subject-template change of the prod slice (`ci-runners.md` §11.5): with infra's default immutable subject it would be a separate condition key that AWS may not evaluate, so this pass moves only the ref to `release`.
- **S2, a spare Elastic IP per pool:** each node pool holds `max + 1` addresses, so a refreshed node always finds a free one while the old node still holds its own (cost: about 3.60 USD a month per spare). **Order and failure (decided 2026-11-04):** the node associates its address **before** the ECS agent may start (the agent's unit waits for the association unit); it retries until it succeeds or 10 minutes pass; at the deadline it logs the reason to the console, runs `systemctl mask --now ecs` and shuts down, so the Auto Scaling group's health check replaces it and a refresh that cannot place a node fails visibly (no node ever runs tasks without an allow-listed address; no new permission). **Alarm:** CloudWatch has no address-attachment metric, so a small function in the `observability` module (under `observability_enabled`, every 5 minutes by EventBridge, free tier) reads each pool's addresses by their `NodePool` tag and the group's running nodes and publishes `NodeAddressesFree` (dimension `Pool`) to `OnePeek/<env>`; the alarm `onepeek-<env>-node-addresses-exhausted` fires when it is below 1 for 30 minutes (the next refresh or scale-out could not get an address), missing data breaching. (Rejected: AWS Config `eip-attached`, paid and always failing on the spare; CloudTrail `DisassociateAddress`, which a termination does not emit.)
- **S3, image retention that keeps rollbacks (rules by ECR priority; an image a higher rule matches is never expired by a lower one):**
  1. `v` tags (promotions): keep the last **15** (first, so an image tagged both `v…` and `sha-…` is kept by its promotion);
  2. `sha-` tags (every release build, `release-ecs.yml`): keep the last **15**;
  3. `buildcache`: keep **1**;
  4. **untagged** images: keep the last **300** by count, no age rule. Cosign stores signatures and SBOMs as OCI 1.1 referrers, which carry no tag, so an age rule would expire the signatures of kept releases; 300 holds the referrers of 30 releases (3 each) plus build-cache leftovers. ECR removes the referrers of a deleted subject image within 24 hours (ECR user guide), so referrers never outlive their image; the count rule stays because an age rule would still expire referrers of **kept** images.
  5. every tagged image (`tagPatternList ["*"]`): keep the newest **40**. ECR's lower rules still **count** images a higher rule matched (they only cannot expire them), so this rule is a combined window over all tags: 15 `v` + 15 `sha-` + 1 `buildcache` = 31 leaves at least 9 for other tags (e.g. full-commit tags from `deploy-ecs.yml`); give any new tag kind its own prefix rule before it is used.
  The emulator follows ECR's documented semantics (lower rules count images higher rules matched, and may only mark the others); a test tells the two models apart (15 full-commit images, then 15 newer `sha-` images and a `buildcache`: rule 5 must keep the full-commit images while under 40). A test evaluates the rules on a sample image list: the 16th `sha-` release expires the oldest, and no referrer of a kept image is expired while under the cap. The sandbox function repositories (immutable, tags from `image_tags`) get rules 4 and 5. The lifecycle policies leave `policy/protected.yaml`'s protected list (the provider replaces a policy on any change, and a policy holds no data); the repositories stay protected, so no plan may delete or replace one.
- **S4, pinned shared workflows point at releases:** callers pin `OnePeek/.github` by commit SHA (the stronger standard), so a `job_workflow_ref` tag rule cannot apply. Instead the pin check (P2) fails CI when a pinned SHA is not the commit of a `v*` tag. The deploy roles' `@*` stays, recorded here.
- **S5, provider allow list:** every CI `terraform init` that runs **with cloud credentials** (plan, apply, drift, canary) runs with `-lockfile=readonly`, (the shared `terraform-checks` init, `-backend=false` with no credentials, is exempt: an unreviewed provider there reaches nothing; modules without a committed lock stay that way), so the committed lock files are the complete list of providers CI can download (an implicit provider, a legacy `required_providers` string, or a `.tf.json` file cannot add one); a pull-request check fails when any `.terraform.lock.hcl` names a provider outside `policy/providers.yaml` (today `hashicorp/aws`, `hashicorp/random`, `hashicorp/tls`, `hashicorp/archive`, `cloudflare/cloudflare`, `mongodb/mongodbatlas`, plus what the repo already uses), before any plan runs.
- **S6, the GitHub App replaces `ORG_READ_TOKEN`:** `onepeek-agents` holds `actions: read` (the lock mint requests it), `contents: read` and `pull_requests: read` (to verify in the App settings) and is installed on every repo CI reads; workflows mint a short-lived token with `actions/create-github-app-token` (scoped to the repos the job names); the personal token is deleted once no workflow reads it. A token a reusable workflow needs is minted inside that workflow (a caller job has no steps), so the release chain changes from the inside out: infra `db-bootstrap.yml`, then `.github` `release-ecs.yml`, then the callers (aws-stack §10 "Cross-repo access").

**Cost and cleanup**
- **D3, hard stops in product accounts:** preprod at 95 USD and sandbox at 25 USD (gross, before credits, like CI's proposed 80 USD; each stop follows its budget, raised from 75 and 15 by the foundation reset, §4 of `foundation-reset-2026-11-05.md`, 2026-11-05) apply an automatic deny policy, `onepeek-<env>-budget-stop`, to `ci-apply` and every deploy role: `ec2:RunInstances`, `ec2:CreateFleet`, `rds:CreateDBInstance`, `rds:CreateDBCluster`, `lambda:CreateFunction`, `lambda:UpdateFunctionCode`, `ecr:PutImage`, `ecr:InitiateLayerUpload`, `ecr:CompleteLayerUpload`, `ecs:RegisterTaskDefinition`, `ecs:CreateService`, `ecs:UpdateService`, `ecs:RunTask`, `ecs:StartTask`, and (so a new role cannot sidestep it) `iam:CreateRole`, `iam:UpdateAssumeRolePolicy`; running services keep running. **Owner, split (decision 182, rulings G1 to G3, §4.1 (orchestrator, provisional, 2026-11-08)):** the stop budget, the stop policy and the action are in the CI-applied account root (`roots/aws/account`); the execution role, its boundary and `ci-stop-guard` stay in `bootstrap/` (applied by the founder's `scripts/up <env> bootstrap`), because `ci-apply`'s boundary forbids changing its own role. The account root owns a **separate stop budget** `onepeek-<env>-stop` (same limit, gross) with the action, so it never depends on the stack's alert budget `onepeek-<env>-monthly` (which the sandbox stack creates and destroys on every run); the alert budget and its alerts (50, 80, 100% actual, 100% forecast) stay as they are. The action's target roles are an explicit list in `config/<env>.yaml` (`budget_stop.roles`: `onepeek-<env>-ci-apply` and the deploy roles by their fixed names), checked by a test against `deploy_repositories`, since one root never reads another's state. The execution role trusts `budgets.amazonaws.com` with `aws:SourceAccount` only: Budgets checks that it can assume the role before the action exists, so an `aws:SourceArn` condition on the action ARN refuses `CreateBudgetAction` (found by the first preprod bootstrap, 2026-11-04); `guards.tf` matches. The budget-action execution role is the **one named exception** to the CI boundary rule (`check_iam_boundary.py` lists it): its own boundary allows only `iam:AttachRolePolicy` / `iam:DetachRolePolicy` on those role ARNs with condition `iam:PolicyARN` = the stop policy, and nothing else. **CI cannot undo it:** in the product accounts a separate policy `onepeek-<env>-ci-stop-guard` attached to `ci-apply` (an explicit deny in an identity policy applies whatever the boundary allows; the boundary itself is at IAM's 6,144-character limit; `ci-apply` cannot detach its own policies) denies executing the stop's budget action (`ExecuteBudgetAction` only; the stop budget and action are CI-managed since decision 182), detaching the stop policy from any role, deleting the stop policy (its new versions are allowed), changing the budget-action boundary and the guard itself, and `iam:*` on the budget-action role except `iam:PassRole` (narrowed by G1 (orchestrator, provisional, 2026-11-08); the CI account keeps its own `guards.tf` role, so these denies are not added there). **Threat model (decided 2026-11-04, provisional):** the stop guards against runaway cost, not a malicious pipeline. Only `ci-apply` carries the guard; a role `ci-apply` creates could in principle lift the stop, but `ci-apply` only applies a reviewed plan from `release`, so doing so takes a reviewed, merged Terraform change that the plan policy and the review both show. Revisit with the layers (slice 1f), where the boundary is split per layer and regains room. The boundary's size is checked by the apply (IAM refuses over 6,144 characters); a rendered-size check in `scripts/check_iam_boundary.py` is a follow-up. Every lock file CI initialises read-only records checksums for `linux_arm64`, `linux_amd64` and `darwin_arm64`. Open risks, checked on the first real bootstrap apply: the target roles are fixed names, and some exist only while their switch is on (sandbox deploy roles, `deploy-db-bootstrap`); `ci-sandbox` joins the list when it is built. Lifting the stop is a founder step (detach the policy, or raise the budget).
- **C2, C6, logs:** the Image Builder groups are declared with 14 days (adopted with `import` blocks whose `for_each` is on only when `runner.import_image_builder_logs` is true in `config/ci.yaml`: true for today's account, where both groups exist; false for a fresh account, which creates them); runner images set journald `SystemMaxUse=200M` and Docker `json-file` 10 MB × 3; nodes already cap Docker logs and gain the journald limit with S2 (same user data, after infra #122).
- **C3, package snapshots:** a shared reusable workflow `package-cleanup.yml` (weekly, `packages: write`, dry run on pull requests) runs **in each publishing repo** (backend-service for `@onepeek/api-client`, onepeek-design-system for `@onepeek/tokens` and `@onepeek/ui`), so its own `GITHUB_TOKEN` owns what it deletes. It deletes `-next.*` snapshots (api-client.md, design-system.md) and `0.0.0-pr<N>.*` previews older than 30 days, keeping the latest 10 of each kind; released versions are never touched. A 403 fails the run (a permission change is visible, never a silent skip); a 404 for a package not yet published is a notice, not a failure.
- **C4:** the archived `frontend-web` deploy role and its `deploy_repositories` entry are removed. `policy/protected.yaml` gains a one-time destroy allowance naming exactly the `["frontend-web"]` instances of the deploy-role resources (dated 2026-11-04), the release pull request carries `founder-approved-destroy` (pre-approved while preprod holds no data), and the allowance is deleted in the next change after that release.
- **C7, the retired `event_bus/sns_sqs_region` setting (foundation reset W5.4; provisional, 2026-11-05):** infra stops publishing it (the backend builds every AWS client with `AWS_REGION`, and there is no `EVENT_BUS_SNS_SQS_REGION` setting, `config-and-secrets.md` §5). Deleting it deletes one instance of a protected resource (`module.stack.module.settings.aws_ssm_parameter.setting`, `policy/protected.yaml`), so, as C4 did for `frontend-web`, `policy/protected.yaml` gains a one-time `destroy_once` allowance dated 2026-11-06 (decision 167) naming exactly `'module.stack.module.settings.aws_ssm_parameter.setting["event_bus/sns_sqs_region"]'` and nothing else. The infra release pull request that carries the delete needs the founder's `founder-approved-destroy` label (the delete still counts as a destroy; preprod holds no data), and the allowance is deleted in the next change after that release. The plan policy test covers it: the allowance lets that one delete through, and the same plan with any other setting deleted, or that one replaced, is still refused.
- **C5, sandbox clean-up before go-live:** the sweep and the scheduled `aws-nuke` of `sandbox.md` §6 are built and tested (dry run in CI) before `sandbox_enabled` is switched on anywhere.

**Process and versions**
- **P1, expand first:** when one repo writes a contract another repo validates strictly (services file, settings, API), the consumer's accepting change ships first, in its own change set, and the producer's set follows. `vanguard ship --order repoA,repoB` overrides the fixed order for this; the default stays as it is. **Declared dependencies:** a pull request whose CI needs another repo's unmerged change says so in its body, one line each: `Depends on: OnePeek/<repo>#<n>`. (1) `vanguard preflight` refuses to push such a branch while a listed pull request is unmerged (keep it local, or open it as a draft); (2) every repo's pull-request workflow starts with a `depends-on` job (small runner, seconds) that fails with "waiting for <repo>#<n>" while one is unmerged, and every other job `needs:` it, so no runner time is spent on a run whose result is already known; (3) `ship_change_set.py` merges the listed pull requests first and re-runs the dependent one. (Lesson L26.) **No CI on a known result (decided 2026-11-04, lesson L27):** (a) **implicit docs dependency:** when the docs pin file names a commit that is not on docs `dev`, the `depends-on` job treats the open docs pull request containing it as a dependency (no line needed): the job passes with a notice while that docs pull request is open, because `ship_change_set.py` merges docs first and refuses code before it (`--strict` fails the wait), and it fails only when the pin is in no open docs pull request (lesson L33); (b) **pins inside a change set:** a code pull request may pin **any commit of its set's docs pull request**; `ship_change_set.py` moves the pin to the docs merge commit as part of the merge, without a separate CI round **only when the green run tested the current base head** (its merge commit's first parent equals the base branch head now); otherwise it waits for the fresh run; `depends-on` reads the pull request's **live body** through the API (a re-run reuses the original event payload); (c) **every pull-request workflow** that runs on our runners starts with `depends-on` and its jobs `needs:` it, not only `checks.yml`; On a run that is not a pull request (push, schedule, dispatch), `depends-on` passes at once with a notice, so the jobs that need it (for example `pins` on push) still run; the shared `workflow-lint.yml` also runs on push to `dev`. (d) the `edited` trigger is dropped (it re-ran every check on a body edit): when a dependency merges, the ship tool re-runs the dependent pull request's checks.
- **P2, pins:** (for callers outside a change set, the pins move once a day through each caller's Dependabot `github-actions` run; §8b's automatic pin-move workflow was never built and is kept only as a design record, decision 180; orchestrator, provisional, 2026-11-10; the text below is the earlier design) after tagging `.github`, `vanguard ship` opens a pin-move pull request in every caller (callers more than one minor version behind get the PR with a note that inputs may need a hand fix). A reusable `pins.yml` job, which every repo calls, fails when the repo's `.github` pins are not all the commit of **one** `v*` tag (this is S4): every `uses:` naming `OnePeek/.github` in any letter case counts, and a ref that is not a 40-character SHA (a branch, a tag name) fails. Pin-move pull requests are safe to re-run (an existing branch or pull request for the tag is updated, never a second one; nothing is deleted locally), a failure in one caller does not stop the others, and every repo whose pins were not moved inside the set (including one merged before `.github`) gets one. `--order` and `Depends on:` never move `onepeek-docs` off first place. There is no docs pin any more (R-DOCS-LOCAL, DOC-1, 2026-11-12). `pins.yml` reads the private docs repo with the App token (S6).
- **P3:** tflint **0.65.0** and uv **0.12.0** (provisional) are pinned in CI and in `vanguard local-ci`. On a laptop uv mismatch, uv fails with the fix. **tflint (refined 2026-11-05, .github#48):** when the laptop's tflint is missing or is not the pinned version, local CI runs each tflint command of a pure-tflint step (every line is a `tflint` command, optionally after `cd <dir>`) as its own `docker run` of the official image `ghcr.io/terraform-linters/tflint:<version>` with the image's own `tflint` entrypoint, the repository mounted at `/data`, the working directory set, a persistent plugin directory mounted at `/root/.tflint.d` (so `--init` holds for the next command) and only `GITHUB_TOKEN` and `TFLINT_*` passed by name. A tflint step that also runs other commands needs native tflint and fails with that reason. With neither the pinned tflint nor Docker, local CI warns; under `local_ci.py --release` (which `preflight.py --release` passes) every optional tool that cannot run, tflint and trivy included, is a failure, also with `--skip-docker`. **Before any step,** local CI fails on an unresolved merge-conflict marker (a line starting `<<<<<<<` or `>>>>>>>`, with or without a label) in any tracked text file. A step that edits `package.json` (`npm pkg set/delete/fix`) gets the file restored afterwards.
- **P4, preflight:** `vanguard preflight <repo> [--release]` runs local CI (and refuses unless it ends `LOCAL CI OK`), the pin checks, the tool versions (`.terraform-version`, Python, Node), and with `--release` every release-only step's prerequisites. **Tokens:** the App's granted permissions (`gh api /orgs/OnePeek/installations`, `apps/<slug>`) against every `create-github-app-token` permission the repo's workflows and the shared ones they call request; the App's installed repositories against the repositories those jobs name (reported "unverified" when the laptop lacks org-admin read); `ORG_READ_TOKEN` and other repository secrets cannot be read from a laptop and are reported "unverified". **Other repos' release state**, for each repo the contract or lock reads: fail when it has more than one open `dev` → `release` pull request, or none while `release` is stale: the last `dev` commit merged into `release` (the second parent of the **newest merge commit reachable from `release`**, so a hotfix squashed on top of it does not count as stale; or `release` itself when it is on `dev`, i.e. fast-forwarded) is not an ancestor of `dev`; no merge commit and not on `dev` also fails ("no release merge found"), which means the check would compare against code `dev` no longer builds on. (`release` itself is never an ancestor of `dev`: releases merge with a merge commit.) **Tool versions:** a mismatch with `.terraform-version`, `.python-version` or `.node-version` fails. ## 8b. Automatic pin moves (foundation reset W4.3; provisional, 2026-11-06) (design record: superseded by decision 180)

**Superseded (orchestrator, provisional, 2026-11-10).** What, Why and everything below were designed on 2026-11-06 and never built. Decision 180 (founder, 2026-11-08, one `.github` pin round a day) replaced them: the daily round is each caller's Dependabot run ("Trigger" below; `delivery-pipelines.md` §9.1 row 1). The founder questions at the end of this section (decision 168) answered the design of the workflow below, not the Dependabot round; the Dependabot pull requests merge through the normal path ("Trigger" below).

**What.** When `OnePeek/.github` cuts a new `v*` tag, a workflow in `.github` opens one pin-move pull request in every caller repo, waits for its checks, and merges it when they are all green, with no person acting. It replaces the pin round that `ship_change_set.py` runs today (§8a P2) for repos outside a change set.

**Why.** A one-line shared-workflow fix needed a tag plus 8 pin pull requests on 2026-11-05 (R3 of the foundation reset), each raised, watched and merged by hand. The pins stay SHA pins (S4); only the moving of them is automated.

**The callers.** The eight repos that pin `OnePeek/.github`: `onepeek-docs` (base `dev`), `onepeek-infra`, `onepeek-design-system`, `backend-service`, `onepeek-web`, `browser-extension`, `mcp-athena`, `plugin-owl` (base `dev`). The list is a constant in the script; a test compares it with the repos `ship_change_set.callers()` finds in the workspace, so a new caller cannot be missed silently. Pins on `release` and `hotfix/*` are never moved here: they move only with a reviewed promotion, which keeps the prod path behind the founder's approval.

#### Trigger

**Replaced by the daily Dependabot run (decision 180; orchestrator, provisional, 2026-11-10).** The workflow below (`pin-move.yml`, `scripts/pin_move.py`, the `pins` job of `tag-main.yml`) was never built and is not built: the one pin round a day (`delivery-pipelines.md` §9.1) is each caller's Dependabot `github-actions` daily grouped run (group `onepeek-shared-workflows`), at Dependabot's default daily slot, one pull request per repo with the newest tag, its own open pull request updated rather than a second opened. `ship_change_set.py` moves no pins outside the change set after a `.github` merge unless `--pin-now` is given and the set's `.github` pull request carries `Lane: hotfix` (the same-day security path); without that lane `--pin-now` is refused before any merge. A Dependabot pin pull request is merged through the normal path, not by a pin-move workflow: the watcher (`vanguard watch`) merges it when its checks pass because Dependabot is a listed author (`authors: [Karan-98-Mehta, app/dependabot]`, `vanguard` `config/ship.yaml:8`, `dev` 3968a8d) (orchestrator, provisional, 2026-11-10). The rest of §8b is kept as the design record.

Workflows started by `GITHUB_TOKEN` events do not start other workflows, and `release-tag.yml` creates the tag and release with `GITHUB_TOKEN`, so `on: push: tags` or `on: release` would never fire. Instead:
- `release-tag.yml` gains the outputs `tag` and `sha` (the tag it created and its commit).
- `tag-main.yml` gains a second job `pins`, `needs: tag`, calling the new reusable `./.github/workflows/pin-move.yml` with that tag and sha, `dry_run: false`, in the GitHub environment `pin-move`.
- `pin-move.yml` also runs on `workflow_dispatch` (inputs `tag`, `sha` optional, `dry_run` default `true`, `repos` default all) for the dry run and for a hand re-run. On a dispatch `sha` is empty unless given; step 2 then uses the commit the tag resolves to and prints it, so the dry run shows what it would move to; `tag-main` always passes `sha`.
- `concurrency`: automatic runs use `{ group: pin-move-auto, cancel-in-progress: false }` and dispatch runs `{ group: pin-move-dispatch-<tag>, cancel-in-progress: false }`, so a dry run or a dispatch for an older tag can never cancel an active automatic run. An automatic run is superseded only after the newer tag is verified: a running older run checks at each poll whether `OnePeek/.github` has a newer `v*` tag (resolved to its commit as in step 2) and, if so, stops itself with the summary "superseded by <tag>"; the newer run, queued behind it, closes the older run's open pull requests (step 3 below).

**When nothing moves.** A tag whose diff from a caller's current pin touches none of `.github/workflows/`, `actions/` and `scripts/` (the code callers run) is skipped for that caller with a summary line; the pin check needs one tag, not the newest (§8a P2), so a caller may stay on an older tag. A tag older than or equal to the caller's pin (by version) is never applied (no downgrade).

#### What each caller's job does (`scripts/pin_move.py`, one matrix job per repo, `fail-fast: false`, GitHub-hosted, `timeout-minutes: 150`)

1. **Token.** `pin_move.py` mints the `onepeek-ci-bump` installation token itself (from the App's key in the `pin-move` environment) for **that one repo** (`repositories: <repo>`), so a job can never touch another repo. An installation token lasts one hour (GitHub docs) and the wait can last 120 minutes, so the script re-mints the same repo-scoped token whenever the current one is older than 45 minutes, before every poll and before the merge; every call uses the newest token.
2. **Tag.** Resolve the tag through the API to its commit (dereferencing an annotated tag) and refuse unless it equals the `sha` input (when one is given; see the dispatch inputs) and matches `v<major>.<minor>.<patch>`.
3. **Old pull requests.** Close every open pull request in the repo whose head branch is `ci/pins-v*` for an older tag and whose author is the App, with a comment naming the newer tag, and delete those branches. A pull request someone else pushed to is left alone (it is no longer an automatic one).
4. **The commit.** Check out the base (`dev`) at its head `B` with `persist-credentials: false`; rewrite every `OnePeek/.github/.github/workflows/<name>.yml@<sha> # <tag>` and `OnePeek/.github/actions/<name>@<sha> # <tag>` line to the tag (the same pattern as `bump_pins.py` and `ship_change_set.rewrite_pins`, shared from one module). Nothing to change ends the job green. Commit `chore: pin OnePeek/.github workflows to <tag> (pin-move)` as the App's bot user, run the **allowlist** (below) on `B..commit`, push `ci/pins-<tag>` with the token in an `http.extraheader` for that push only.
5. **The pull request.** Open it into the base. The body says it was opened and will be merged by `pin-move`, names the old and new tags and links the `.github` release notes, and carries `Lane: feature`.
6. **Wait for green.** Poll every 30 s, up to 120 minutes (an infra pull request that triggers the sandbox gate takes about 75). Green uses the merge tool's rule, imported from one module, `scripts/merge_gate.py` (extracted from `ship_change_set.wait_green` and `checks`, which then import it): the checks on the head are compared with the **expected required checks** for that repo and base (the same list the merge tool uses today to decide which checks are required, read by `merge_gate.required_checks(repo, base)`): green only when every expected check has reported for the current head and is `success` or `skipped`; an expected check that has not reported is pending, never ignored, so a non-empty list of green checks is not enough; any `fail` or `cancel` is red; the AI review is excluded. When an expected check is still missing after 10 minutes the job fails as "required check <name> not reported". It never re-runs a check (the App has no `actions: write`); a spot reclaim is re-run by the repo's own `spot-rerun-caller.yml` (`ci-runners.md` R1).
7. **Re-check, then merge.** Read the pull request again and merge only when: it is open; its branch contains the base's current head (the pull request's `base.sha` equals the base branch head now, so the green checks ran on exactly the tree being merged; if the base moved, the job updates the branch, which starts new checks, and goes back to step 5); its head is exactly the commit pushed in step 4; its author is the App; its base is `dev`; its files and patch, read from the API, pass the allowlist again. Merge with `PUT /repos/<repo>/pulls/<n>/merge`, `sha` set to that head (GitHub refuses if the head moved), method `squash` (`merge` for `onepeek-docs`, whose rule is a merge commit). Then delete the branch.

**The allowlist (never a non-pin change).** The diff from `B` to the commit (and the pull request's API patch at merge time) passes only when all hold:
- every changed path matches `.github/workflows/<file>.yml` or `.yaml`; no file is added, deleted, renamed or has its mode changed; the docs pin file is not in the diff (stated explicitly, though the path rule already excludes it);
- with zero context lines, every hunk removes exactly as many lines as it adds, and each removed line, paired in order with its added line, is a pin line whose text is identical except for the 40-character SHA, which becomes the tag's commit, and the trailing `# <tag>` comment, which becomes `# <new tag>`;
- the new tag is newer than each old one.
Anything else refuses, closes the pull request with the reason, and fails the job.

#### Failure handling

| What | What happens |
|---|---|
| A check is red, or still pending at 120 minutes | The pull request stays open; the job comments on it with the failed checks and the run link, then fails. The `.github` `tag-main` run is red with a per-repo summary table (GitHub mails the founder on a failed run). Fix forward: a person pushes the fix to that branch, which turns it into an ordinary pull request merged with `ship_change_set.py` after review (step 7 refuses a moved head). A newer tag supersedes it. |
| The merge is refused because the base moved and the merge conflicts | Once: rebuild the commit from the new base head (step 4 to 7, same branch name, the old pull request closed). A second refusal fails the job. |
| The App is not installed on a repo, or the token cannot be minted | That repo's job fails; the others go on. |
| The allowlist refuses | The pull request is closed with the reason; the job fails. |
| A newer tag starts while a run waits | The older run stops itself at its next poll once the newer tag is verified (concurrency never cancels it); the newer run closes its pull requests in step 3. |

**Interaction with `ship_change_set.py`.** Pull requests inside a change set still get their pins moved on their own branches right after `.github` merges and tags (so they test against the new workflows). (orchestrator, provisional, 2026-11-10) With the daily Dependabot round, callers outside the set are not moved by the tool (Dependabot moves them in its next daily run), except with `--pin-now` on a `Lane: hotfix` `.github` pull request, which runs the §8a P2 moves as before; there is no `pins` job to wait for. Not: Actions (no re-runs), Administration, Issues, Secrets. Its private key is stored as an environment secret of the `pin-move` environment in `OnePeek/.github`, whose deployment branch rule admits only `dev`, so only `tag-main` runs on `dev` (and a dispatch from `dev`) can read it; a pull request run in the public `.github` repo never can.

## 8c. Local CI that matches CI (follow-ups of 2026-11-05 and 2026-11-06; provisional, 2026-11-06)

`OnePeek/.github` `workspace/local_ci.py` is the "push only on `LOCAL CI OK`" gate (AGENTS.md "Running agents" item 6). Four gaps let it say OK where CI then failed. Each fix below has a test in `scripts/test_local_ci.py` that fails on regression.

**L1, Terraform tests were skipped by a comment.** `REMOTE` (the pattern for steps that need GitHub or AWS) is matched against the whole step text, comments included. Infra's Terraform-tests step has a comment containing `aws ` followed by a space, so `\baws \b` matched and the step was always skipped (the cause of infra #170's CI failure, 2026-11-05).
- `REMOTE` and every other skip pattern are matched against the step **with shell comments removed**: whole-line comments, and a `#` that starts a word outside quotes to the end of the line (a small shell-aware scanner, line by line: a `#` starts a comment only at the start of a word, that is at line start or after unquoted whitespace, and never inside single or double quotes; `shlex` comment mode is not used, because it treats a `#` inside a word as a comment, which the shell does not, so `echo url#fragment; aws s3 rm …` would hide the `aws` command; a test covers exactly that line; a line the scanner cannot parse is kept whole, so the fix never hides text; review of docs #236).
- A step that runs `terraform test` is never skipped silently: when a skip rule still matches it, the run fails with the reason under `--release` and prints `WARN ... terraform test skipped: <rule>` otherwise. The final summary lists skipped `terraform test` steps first.
- Tests: infra's real Terraform-tests step text (copied as a fixture with its comment) is run, not skipped; a step whose code (not comment) calls `aws s3` is skipped; a `#` inside quotes (`echo "#aws "`) is kept as code; `--release` fails on a skipped `terraform test`.

**L2, script tests ran on the Mac's bash 3.2.** CI runs Linux with bash 5; macOS ships bash 3.2, and `.github` #54's tests exited 1 on the Mac and 120 on Linux (a test stub that did not read stdin got SIGPIPE only on Linux, 2026-11-06).
- On macOS, a job whose steps run script tests (`python -m unittest` or `pytest` over `scripts/`, or any `*.sh` or `bash` script) runs those steps in a Linux container instead of on the laptop: image `onepeek-local-ci`, built from `workspace/local-ci/Dockerfile` (Ubuntu 24.04 from ECR Public pinned by digest, bash 5, Python 3 with PyYAML, Git, jq, curl, shellcheck, matching the runner image's versions where `ci-runners.md` §8.4 names them), tagged with the SHA-256 of the Dockerfile so a changed Dockerfile is always rebuilt and never stale. The repo is mounted read-write at the same path, the step's environment is passed by name, `--network none` unless the step reaches a registry, never Docker-in-Docker: a step that itself calls `docker` runs on the laptop as today.
- `--native` turns this off; without Docker the run fails under `--release` and warns otherwise.
- Tests: the job selection (a `unittest` step over `scripts/` runs in the container; an `eslint` step does not); the image tag changes when the Dockerfile changes; a fixture test that reads `$BASH_VERSINFO` reports 5 inside the container.

**L3, a stale image tag stood in for a build.** `uses:` steps are skipped, so `docker/build-push-action` never runs locally, and the next `run:` steps (backend `image-smoke.yml` smoke and boot, web `image.yml` boot) ran against whatever image the laptop last built under `onepeek-backend:smoke` or `onepeek-web:boot`.
- A `docker/build-push-action` step with `load: true` and `push: false` is translated into `docker buildx build --load` with its `context`, `file`, `platforms`, `tags`, `build-args` and `secrets` (an `npm_token` secret from the laptop's `gh` login with `read:packages`, as P8 does for installs), with the expressions the run knows filled in. Before it, every tag it names is removed (`docker image rm -f`).
- When a build cannot be translated (an unknown input, a secret the laptop cannot supply, `--skip-docker`), its tags are removed and every later step of the job that names one of them is skipped with "needs the image a skipped build makes". No step ever runs on an image this run did not build.
- Tests: a fixture job (build, then a `docker run <tag>` step) builds first; with the build untranslatable, the `docker run` step is skipped and an existing image of that tag is removed first; `push: true` is never translated.

**L4, the shared workflows came from the shared checkout, not the pin.** For a reusable-workflow job, local CI reads the workflow (and the runner-label lint) from `<workspace>/.github`, at whatever branch that checkout is on, while CI runs it at the caller's pinned SHA. A caller was checked against unmerged or older shared code.
- By default, each pinned `uses: OnePeek/.github/...@<sha>` is read from a detached, temporary worktree of `<workspace>/.github` at that SHA (fetched when missing; removed at exit), so local CI runs exactly what CI runs. The runner-label lint runs from the same worktree.
- `--shared <path>` (or the environment variable `ONEPEEK_SHARED_GITHUB=<path>`) uses a given `.github` worktree instead, for testing a caller against an unmerged `.github` branch; the summary then says `shared workflows from <path> (<branch> <sha7>), not the pin`, and `preflight.py` refuses `--release` with it. `ONEPEEK_WORKSPACE` keeps its meaning (the folder holding the repos) and is still removed from the steps' environment.
- `local_ci.py` resolves its repo argument from the current directory and prints the absolute path it runs on first (an agent ran it on the shared checkout instead of its worktree on 2026-11-06).
- Tests: a caller pinned at commit A while the checkout is at B runs A's steps; `--shared` runs B's and prints the notice; a pin SHA missing locally is fetched, and an unknown one fails; the worktree is removed after the run and after a SIGTERM.

**Files to change.** `OnePeek/.github`: `workspace/local_ci.py`, `workspace/local-ci/Dockerfile`, `workspace/preflight.py` (refuse `--release` with `--shared`), `scripts/test_local_ci.py`, and §8a P8 of this playbook points here.

### 8d.1 Grafana: the official MCP server, read-only
- **Server:** `grafana/mcp-grafana`, the official one, pinned: version and the SHA-256 of its `darwin_arm64` release archive in `OnePeek/.github` `workspace/mcp/versions.json`. A Dependabot-style bump is a reviewed pull request (P15).

It reads the token with `security find-generic-password -s onepeek-grafana-viewer -w` (the token comes back on the subprocess's stdout, never in arguments), and the expiry from the item's comment. It refuses with a clear message when the token is missing or expired, and warns on stderr in its last 5 days. Then it `exec`s the server with `GRAFANA_URL=https://radiantthyme190.grafana.net` and the token in `GRAFANA_SERVICE_ACCOUNT_TOKEN`, in the server's environment only, over stdio ([mcp-grafana README](https://github.com/grafana/mcp-grafana)).
- **Flags** (from the same README; the launcher's test checks each against the pinned release's `--help` and fails when one is missing): `--disable-write`; `--enabled-tools` set to the categories search, datasource, dashboard, loki, prometheus, tempo, alerting and navigation (CloudWatch, admin, incident, OnCall, Sift, annotations, folders and every other category stay off); `--max-loki-log-limit 500` (the default is 100); `--disable-api` with `--loki-enforced-matchers '{deployment_environment_name=~"preprod|sandbox"}'` (the README says the matcher needs `--disable-api`), so a native Loki query can never read another environment's streams even if one reached the stack.
- **Registration:** `setup.py` links `workspace/mcp.json` to `<root>/.mcp.json`, which holds one server: `{"mcpServers": {"grafana": {"command": "python3", "args": ["<the installed launcher path>"]}}}` (written by `vanguard install`, decision 175). No token, URL secret or environment value is in it. Claude Code asks each person once to approve a project server. `setup.py --check` fails when `.mcp.json` is missing or differs, and when the keychain item is missing it prints the `grafana_token.py set` step (a warning, not a failure, so a teammate without Grafana access can still work).
- **Three locks on writes:** the Viewer role (Grafana refuses every write server-side); `--disable-write` (the server does not offer write tools); and the P19 hook (8d.3), which allows only the `mcp__grafana__*` tools on its exact list.
- **Scope:** one Grafana stack holds preprod (and the sandbox when its telemetry is on). Prod sends no logs there (the `grafana_logs_enabled` schema rule, `aws-stack.md` §10.11 L1), and prod's stack is decided at launch (question L-Q3).

### 8d.2 CloudWatch: the `log-reader` role through one wrapper
- **Wrapper:** `OnePeek/.github` `workspace/logs.py <env> <command> …`, standard library only, which runs the `aws` CLI with `--profile onepeek-<env>-log-reader --region ap-south-1 --output json` (and `--region us-east-1` for the second `alarms` call). Only `preprod` and `sandbox` are accepted; any other environment is refused before any call.
- **Commands (the whole list):**

| Command | AWS call | Notes |
|---|---|---|
| `groups [--prefix app/]` | `logs describe-log-groups --log-group-name-prefix /onepeek/<env>/<prefix>` | `security*` names are left out of the output |
| `streams --group <g> [--limit 20]` | `logs describe-log-streams --order-by LastEventTime --descending` | |
| `query --groups <g>[,<g>…] --since <dur> [--until <dur>] '<Logs Insights query>'` | `logs start-query`, then `get-query-results` every 2 s, `stop-query` at 60 s | groups may end in `*` (expanded with `describe-log-groups`, `security*` removed, at most 50 a call, split above) |
| `filter --group <g> --since <dur> [--pattern '<filter pattern>'] [--limit 500]` | `logs filter-log-events --start-time --end-time` | |
| `get --group <g> --stream <s> --since <dur>` | `logs get-log-events --start-time --end-time --start-from-head` | |
| `alarms [--state ALARM\|OK\|INSUFFICIENT_DATA] [--prefix <p>]` | `cloudwatch describe-alarms --alarm-name-prefix onepeek-<env>-<p>`, in `ap-south-1` and in `us-east-1` | the uptime alarm `onepeek-<env>-not-ready` is in `us-east-1` (`aws-stack.md` §10.11 L7b); output names the region |
| `alarm-history <name> --since <dur>` | `cloudwatch describe-alarm-history --start-date --end-date`, in the alarm's region | |
| `find --support-ref <XXXX-XXXX-XXXX> \| --trace-id <hex> \| --job-id <id> --since <dur>` | one `query` over `app/*` | the recipes of 8d.4, built in |

- **The time window is forced here.** Every command that reads events needs `--since` (`15m`, `1h`, `6h`, `24h`; at most 24 hours; `--until` defaults to now and must be later than `--since`). A window over 24 hours, or a start more than 14 days back, is refused. IAM cannot force this (`aws-stack.md` §10.11 L7b), so it is a guard: the hook (8d.3) steers agents to this wrapper.
- **Groups are relative.** `--group app/api` means `/onepeek/<env>/app/api`; an absolute name, `..`, a group outside `/onepeek/<env>/`, and `security` or `security/…` are refused (the role refuses them too).
- **Output** is one JSON object a line, at most 1,000 events and 200 KB, then a `{"truncated": true, …}` line, so a broad query cannot flood the agent's context. The lines are already redacted by the app and, for collector lines, by the collector.
- **The single sign-on login** stays a person's step: when the source profile's session has expired, the wrapper prints `aws sso login --profile <source profile>` and exits 3. It never starts a login itself.
- **Why not the AWS CloudWatch MCP server:** its tools take any time range and include calls beyond the nine this role grants, so the window could not be forced in one place and the hook would have to parse each tool's arguments. One wrapper with a fixed command list is smaller to review and to test.
- **Tests** (`scripts/test_logs_wrapper.py`, a fake `aws` on `PATH` that records its arguments and reads its stdin): each command builds exactly the call in the table with the profile, region and window; `alarms` makes both regional calls; `prod`, `--since 25h`, `--since 15d`, `--group /onepeek/prod/app/api`, `--group ../x`, `--group security`, `--group security/egress-proxy`, `query --groups 'secur*'` and an unknown command are refused before any call; `groups` and a `*` expansion drop `security*` names; a query still running at 60 s calls `stop-query` and prints the partial result; output stops at 1,000 events; an expired session exits 3 with the login hint; `find --support-ref ABCD-1234-EF56` builds the query of 8d.4.

### 8d.3 The P19 hook: read commands allowed, everything else refused
Today `workspace/hooks/p19_guard.py` (on `feat/cancel-release`) refuses only the cancel and dispatch commands, returns 0 (allow) on input it cannot parse, and P19's cloud rules are not built. This change builds them, with the log exception, and makes the whole hook fail closed (pitfall 14).
- **Which sessions: all of them.** The cloud rules apply to every session, the coordinator's main session included. The Claude Code hooks reference documents `agent_id` and `agent_type` as identifying a sub-agent (or an in-process teammate, or a `--agent` session), and says nothing about when they are absent ([Claude Code: hooks reference, "Common input fields"](https://code.claude.com/docs/en/hooks)). A rule that applied only when `agent_id` is present would fail open if the field were missing, so no rule depends on it. The cancel and dispatch rules keep applying to every session, as today.
- **Fail closed.** Input that is not JSON, is not an object, has no `tool_name`, or is a `Bash` call with no string `tool_input.command` is refused (exit 2, with the reason on stderr; exit 2 blocks a `PreToolUse` call, the same reference, "Exit code 2 behavior per event"). A `Bash` line the splitter cannot fully split (an unclosed quote, a heredoc, `eval`, `source`, `.`) is refused when any of its words is a refused program name. A tool name the hook has no rule for (Read, Edit and the rest) passes, as today.
- **Bash: allowed (exactly).** `python3 <path>/logs.py <preprod|sandbox> <command> …` (also with `-I`), where `<path>` resolves, against the event's `cwd`, with `os.path.realpath`, to the same file as `realpath(<hook folder>/../logs.py)`, so a copy or a look-alike named `logs.py` elsewhere is refused; `<command>` is in the 8d.2 list. The hook checks the path, the environment word and the command word itself; the wrapper checks the rest. It may pipe only into `jq`, `head`, `tail`, `grep`, `wc`, and `sort` with no flags but `-n`, `-r`, `-u`, `-k` and `-t` (so no `-o`/`--output` and no `--compress-program`, which runs a program); each reads stdin and writes stdout only. `less` and `more` are refused (they can start a shell), and so is any other program after the pipe.
- **Bash: refused**, with the reason and the pointer to the wrapper, in every segment the existing splitter finds (`;`, `&&`, `|`, `$(…)`, back-ticks, `bash -c`, `env X=… cmd`):
  - `aws` with any arguments, raw `aws logs` reads included (they cannot force the window). This includes the coordinator's own read-only `aws` reads and the node diagnostics of `aws-stack.md` §10.8, which a person now runs, until a wrapper exists for them (question F-Q1);
  - `terraform` except `fmt`, `validate`, `version`, `providers`, `test` and `init -backend=false` (everything else can reach a real backend or provider);
  - the other cloud CLIs: `gcloud`, `gsutil`, `az`, `cloudflared` (any subcommand), `wrangler`, `flarectl`, `atlas`, `mongocli`, `mongosh` and `mongo` with a `mongodb+srv://` or `*.mongodb.net` argument, `psql` with a `*.rds.amazonaws.com` host, `grafanactl`, `grr`, `logcli`, `sam`, `cdk`, `eksctl`, `session-manager-plugin`;
  - `curl`, `wget`, `http`, `xh` to `*.amazonaws.com`, `*.grafana.net`, `api.cloudflare.com` or `cloud.mongodb.com`;
  - `python`, `python3` or `node` whose inline code (`-c`, `-e`) names `boto3`, `botocore` or `@aws-sdk`;
  - `security` with `find-generic-password`, `find-internet-password`, `dump-keychain` or `export`, and any `security` command that names `onepeek-grafana-viewer` (only `grafana_launch.py` reads the token, and it runs as the MCP server's process, which this hook never sees);
  - `ps` with an environment flag (`e`, `-E`, `eww`), which would print the MCP server's token from its environment;
  - `logs.py` with `prod` or any environment but `preprod` and `sandbox`.
- **MCP tools, in every session.** A second matcher, `mcp__grafana__.*` (the reference's form for every tool of one server), allows only the read tools on an exact list in the hook: `search_dashboards`, `search_folders`, `get_dashboard_by_uid`, `get_dashboard_summary`, `get_dashboard_panel_queries`, `get_dashboard_property`, `list_datasources`, `get_datasource`, `query_loki_logs`, `query_loki_stats`, `query_loki_patterns`, `list_loki_label_names`, `list_loki_label_values`, `query_prometheus`, `query_prometheus_histogram`, `list_prometheus_metric_names`, `list_prometheus_metric_metadata`, `list_prometheus_label_names`, `list_prometheus_label_values`, `search_tempo_traces`, `get_tempo_trace`, `query_tempo_metrics`, `list_tempo_attribute_names`, `list_tempo_attribute_values`, `alerting_rules_read`, `generate_deeplink` (names from the [mcp-grafana README](https://github.com/grafana/mcp-grafana); the hook's test checks each against the pinned release's tool list). Every other name is refused, so `query_cloudwatch`, `query_cloudwatch_logs` and any new tool are refused by default: agents read CloudWatch only through `logs.py` and its window. A third matcher, `mcp__.*`, refuses any tool of a server whose name contains `aws`, `cloudwatch`, `cloudflare`, `atlas` or `mongodb`, so a later server cannot open a second path.
- **What it is, honestly.** A guard against mistakes, not a security boundary. An agent can write a script file and run it, and every session shares `~/.aws`, whose read-only single sign-on cache any script can use. The boundaries are the roles themselves (`log-reader` and the read-only login only read, and CloudTrail records every call) and the Viewer token, which can only view. That this gap stays open is founder question L-Q1 (`aws-stack.md` §10.11). The P19 row stays "partly built" for that reason.
- **Settings:** `workspace/settings.json` gains the `mcp__grafana__.*` and `mcp__.*` matchers on the same script; `setup.py --check` already fails when the hook is not registered.
- **Tests** (`scripts/test_p19_guard.py`, extending the cancel tests, which stay unchanged), each in a session with `agent_id`, without it, and without `agent_type`, with the same result: allowed: each `logs.py preprod <command>` form through the real path and through a relative path from another `cwd`, `logs.py sandbox query … | jq .`, `terraform fmt -check`, `terraform test`; refused: a `logs.py` copy in `/tmp`, `logs.py preprod groups | less`, `logs.py preprod groups | sort -o x`, `logs.py prod alarms`, `logs.py staging groups`, `aws logs filter-log-events …`, `aws cloudwatch describe-alarms --profile onepeek-preprod-readonly`, `aws s3 ls`, `AWS_PROFILE=x aws ecs describe-services`, `bash -c "aws sts get-caller-identity"`, `echo "$(aws ssm get-parameter …)"`, `logs.py preprod groups; aws s3 ls`, `logs.py preprod groups | sh`, `terraform apply`, `terraform plan`, `terraform state rm x`, `cloudflared tunnel list`, `gcloud auth list`, `mongosh "mongodb+srv://x.mongodb.net"`, `curl https://x.grafana.net/api/search`, `python3 -c "import boto3"`, `logcli query '{}'`, `security find-generic-password -s onepeek-grafana-viewer -w`, `ps eww`, and `gh run cancel 1`. Fail closed: input `not json`, `[]`, `{}`, a `Bash` event with no command, and a line with an unclosed quote that holds `aws` are refused. MCP: `mcp__grafana__query_loki_logs` and `mcp__grafana__list_datasources` allowed; `mcp__grafana__query_cloudwatch_logs`, `mcp__grafana__query_cloudwatch`, `mcp__grafana__update_dashboard`, `mcp__grafana__create_incident` and `mcp__grafana__frobnicate` refused; `mcp__awslabs_cloudwatch__get_log_events` refused. ### 8d.4 How an agent debugs
Start in Grafana (one screen). Go to CloudWatch, through `logs.py`, for what Loki does not hold: one-off tasks, node boot and ECS events. Security lines (sign-in, PDP, break-glass, egress decisions) are a person's to read. Always the smallest window that covers the problem; widen only when it finds nothing.

- **From a `support_ref`** (a user quotes `ABCD-1234-EF56`; `platform/telemetry.md` §8.3): the trace ID starts with the 12 hex characters `abcd1234ef56`.
  - Loki (MCP `query_loki_logs`): `{deployment_environment_name="preprod"} |= "abcd1234ef56" | json | trace_id=~"abcd1234ef56.*"` over the last 6 hours. The line filter only narrows the scan; the match is on the parsed `trace_id` field, so it does not depend on how the JSON is spaced. The lines give the service, the event, the `reason_code` and the full `trace_id`.
  - Tempo (MCP `get_tempo_trace`, or the link `generate_deeplink` builds): the full trace ID. The trace shows each hop: request, outbox, event handler, job.
  - CloudWatch, for an app line: `logs.py preprod find --support-ref ABCD-1234-EF56 --since 6h` runs `fields @timestamp, service, event, reason_code | filter trace_id like /^abcd1234ef56/ | sort @timestamp asc | limit 200` over `app/*`. `find` reads only `app/*`, so a one-off line needs its own query: `logs.py preprod query --groups one-off --since 6h 'fields @timestamp, @logStream, event, reason_code | filter trace_id like /^abcd1234ef56/ | sort @timestamp asc | limit 200'`. Node lines carry no trace ID, so read `node/boot` by time instead, with step 4 of the deploy recipe below over the minutes around the trace's lines.
- **From a `job_id`:**
  - Loki: `{deployment_environment_name="preprod", service_name="worker"} |= "<job_id>" | json | job_id="<job_id>"`. The lines are `job.started`, the handler's own lines, `job.failed` (with `error.stack`), then `job.retry` or `job.dead_lettered` (`platform/jobs-and-schedules.md` §12.1). Their `trace_id` is the trace that created the job; follow it to the request or schedule that enqueued it, as above.
  - CloudWatch: `logs.py preprod find --job-id <job_id> --since 24h`, which runs `fields @timestamp, event, level, job.attempt, reason_code, fields.next, error.type | filter job.id = "<job_id>" | sort @timestamp asc` over `app/worker`.
- **From a failed or stuck deploy:**
  1. `logs.py preprod alarms --state ALARM` (stuck deploy, daemon under capacity, deploy alarms, and the `us-east-1` uptime alarm).
  2. The ECS events: `logs.py preprod query --groups infra/ecs-events --since 2h 'fields @timestamp, detail.group, detail.eventName, detail.reason, detail.stoppedReason, detail.stopCode, detail.containers.0.name, detail.containers.0.exitCode, detail.containers.0.reason | sort @timestamp desc | limit 100'`. `CannotPullContainerError` means an image or a proxy problem; `exitCode` 78 means the app refused its configuration; `Essential container in task exited` with a health-check `stopCode` means `/health` failed.
  3. The service's own last lines before the stop: Loki `{deployment_environment_name="preprod", service_name="api"} | json | level=~"error|critical"` over the deployment's window; for a one-off, `logs.py preprod query --groups one-off --since 2h 'fields @timestamp, @logStream, event, reason_code, fields.variable, fields.error_class | filter level in ["error","critical"] or event = "config.refused"'`.
  4. A node problem: `logs.py preprod query --groups node/boot --since 2h 'fields @timestamp, @logStream, @message | sort @timestamp desc | limit 200'`.
  5. Refused egress lives in `security/egress-proxy`, which agents do not read (decision 172): ask the coordinator, who asks a person.
- **When to stop and ask the coordinator:** anything that needs a write (a restart, a redeploy, a rerun), node diagnostics (`aws-stack.md` §10.8), prod, a security line, a window over 24 hours, or a log group the role cannot read.

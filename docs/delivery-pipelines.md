# LLD: Delivery pipelines

## 1. Purpose and scope
How code in each repo becomes running services: the CI checks, the release workflow per repo, the redeploy and rollback buttons, promotion to prod, the GitHub OIDC roles, CI-minute rules, and how the merge rule interacts with all of it. It replaces `preprod-runtime.md` §6 and the current `release.yml` files in `backend-service`, `frontend-web` (now `onepeek-web`) and `onepeek-infra`.

**In scope:** `backend-service`, `onepeek-web`, `mcp-athena` (its own `mcp` image and service, decision 130), `onepeek-design-system`, `onepeek-infra`, and the shared workflows in `OnePeek/.github`. **Out of scope:** extension store submission, `plugin-owl` tagging (unchanged, `branching-and-delivery.md` §5), and the content of each test suite (module LLDs).

## 2. Responsibilities and non-responsibilities
| Responsible for | Not responsible for (owner) |
|---|---|
| Workflow steps, gates, roles and their trust | The tests themselves (each repo) |
| Image build, scan, SBOM, signing, verification (DP5) | Registry and key resources (`aws-stack.md` §8.8, ECR) |
| Rollout order and watch (DA1, DP7) | ECS rollout mechanics (`aws-stack.md` §6.3) |

## 3. Use cases
### UC-DEL-001: Release the backend to preprod (DA1, DP4–DP7)

**Job layout (foundation reset W2.1, 2026-11-05).** The rows below are steps; `release-ecs.yml` groups them into stages, because every job waits about a minute for a runner. **prepare** (rows 0–1: the scope's lock key, the release order and the newer-commit skip, then the version; `foundation-playbook.md` §5.4a); **build** (rows 2–4 and the digest read-back), as two exclusive jobs `build-image` and `build-web` with the same steps, because only the web build's token may hold `packages: read`; **db-bootstrap** (row 4b, infra's reusable workflow under its own role, so its own job); **deploy** (rows 5, 6, 6b and UC-DEL-005 assets, one step each with its own time limit); **verify** (rows 7–9; it also runs after a deploy that failed once the rollout began, and then only rolls back); **finish** (row 10 notify and the unlock, always; after a cancel it first undoes the release from the lock record's phase, `foundation-playbook.md` §5.4a "Rollback on cancel", provisional 2026-11-05); **api-client** (row 11, backend only, the only job with `packages: write`). Eight jobs are defined; a backend release runs at most 7, a web release at most 5 (one build job is always skipped, and a skipped job takes no runner). A re-run is always "re-run all jobs" (the lock-attempt check refuses partial ones): the build reuses the `sha-<12>` image, signing is skipped when the digest is recorded, migrate and the rollout run again, assets are a no-op when present. Extra images (`extra-images`) are refused by the build step until the sandbox Dockerfile exists (§16); when it does, they are built by a loop in the build step, not a matrix (matrix outputs are last-writer-wins). No registry password is handled for the scan: Trivy authenticates to ECR from the role's AWS credentials (`ecr:GetAuthorizationToken`). **verify** gives every step before the rollback its own `timeout-minutes` (the caller's smoke script 10), and its job limit exceeds their sum, so a hanging check ends as a failed step and the rollback still runs (a job timeout would cancel the job and skip it). No step in build, deploy or verify before the rollback carries `always()` or `cancelled()`, so the lock-attempt check gates every change. **Phases (W2.7, provisional 2026-11-05, revised after review round 1):** every write is a conditional write on the run's own record (`foundation-playbook.md` §5.4a), and a run whose write fails has lost the key and stops at once. `deploy` writes `migrating` with no ARN **before** row 5's `run-task`, starts the task with `--started-by <run_id>-<run_attempt>`, then writes the ARN, and writes `locked` once the task has stopped; it writes `rolling` with `previous` and `previous_lambda` before the first `update-service` of row 6. `verify` (job `if:` includes `!cancelled()`) writes `done` once smoke and watch pass, or `locked` once its rollback is stable. `finish` acts on the phase it reads, never on `cancelled()`: a killed runner fails a job without cancelling the run, and a cancelled or killed job may never publish its outputs. A record still `rolling` gets the put-back; the key is freed only when the put-back succeeded, and is otherwise left `rolling` for `cancel-release.yml` (UC-DEL-009).
Trigger: until launch, the push to `release` in `backend-service` (the merge of a `dev → release` pull request: until launch `release` is preprod, `foundation-playbook.md` §5.4 "Until launch, `release` is preprod"; corrected 2026-11-05); from launch, the push to `dev` (every merged pull request; founder, 2026-11-03), in GitHub environment `preprod` (deployment branch `dev`). The first job takes the release lock of its scope (`locks/backend.json`, `foundation-playbook.md` §5.4a; the single `locks/release.json` of §5.4 until the migration there ends), after the release order says the earlier scopes are settled, and an `always()` job releases it. A preprod deploy is identified by `sha-<12>`; the SemVer tag is cut on promotion (`foundation-playbook.md` §5.2), so the `version` job below checks the tag only on promotion. Shared workflow `release-ecs.yml`, jobs in order:

| 8 | `watch` | 10 minutes: poll the alarms of the services this release rolled, `onepeek-<env>-deploy-<service>-*` (`aws-stack.md` §10.4, §16), every 30 s. ECS rolls back on its own **during** the rollout (deployment alarms); this job covers the 10 minutes **after** it is stable, which ECS does not. | 10 | `notify` | The notice is the run summary plus a GitHub deployment record for `preprod` (success or failure, with the commit, digests, durations and the time from merge to running); the `version` job writes the start. | 11 | `api-client` | Only after `verify` succeeded (so a prerelease always names a released backend, which is why web has no pin edge, `foundation-playbook.md` §5.4a). ### UC-DEL-002: Redeploy or roll back one named service (DA1)
`operate.yml`, `workflow_dispatch` from `dev` (preprod) or `release` (prod), inputs:

| Input | Type | Values |
|---|---|---|
| `action` | choice | `redeploy`, `rollback` |
| `service` | choice | the services-file names plus `all` (every long-running service, used by the key-revocation runbook, `platform/security.md` §16 step 2), generated into the workflow by a CI check that fails if the list drifts |
| `environment` | choice | `preprod`, `prod` (prod runs only from `release`, in environment `prod`; any writer can start it, but it can deploy only a digest that already carries the build signature and the promotion attestation, so the risk is availability, not integrity) |
| `version` | string, optional | rollback target: a commit `sha-<12>` (preprod) or `v<version>` (prod); default the previous recorded deployment of that environment |
| `reason` | string, required | written into the deployment record |

It takes the lock key of the service's scope (its `image` in `taskdef/index.json`) and refuses a service whose scope's owning repo is not the caller's repository, so `all` means every long-running service of the caller's own scope and takes one key (were it ever to take more, it would take them try-or-release in the order `backend`, `web`, `mcp`). It writes the same phases as a release and its `finish` acts on them the same way (`foundation-playbook.md` §5.4a; provisional, 2026-11-05). `redeploy` = `update-service --force-new-deployment` (same revision; picks up rotated secrets and changed settings) + watch. `rollback` = resolve the digest of `version`, verify its signature, register from the **current** template with that digest (through the same render and drop check as a release), `update-service`, smoke, watch. Expand/contract (DP6) keeps the old code valid on the new schema; the N-1 test proves it before each release.

### UC-DEL-003: Promote to prod (DP2)
`promote.yml`, run **only** by the push of a merged `dev` → `release` pull request (no free-text `version` input; a `workflow_dispatch` exists only to re-run a failed promotion of the commit that is already the head of `release`, and refuses anything else). It promotes exactly the digests recorded for the merged `dev` commit, job in GitHub environment `prod` (deployment branch `release` only). GitHub Team has no required reviewers on environments in private repos, so the approval is the pull request: the `release` ruleset requires the founder's CODEOWNERS approval, and prod roles trust only `environment:prod` (`foundation-playbook.md` §5.3); a named second approver joins CODEOWNERS from launch. Preconditions checked first: the GitHub deployment of that commit to preprod is `success` and its watch passed; the release-please version for it has no tag yet. Then: (1) resolve the preprod digest; verify the signature; `cosign copy` the image **by digest** into the prod registry (the digest does not change) and write the prod promotion attestation; (2) record the promoted digest in SSM `/onepeek/prod/release/backend/{digest,version}` for `ci-apply`, which alone registers prod `db-bootstrap` and `db-rotate` revisions (UC-DEL-007); (3) prod `migrate` (it stops with `login_missing_run_bootstrap` on a first promotion, exactly like the preprod first-environment order, `aws-stack.md` §8.2); (4) rollout of every service; (5) register the prod **`ops`** revision with the same digest, again after verifying signature and attestation (prod's equivalent of step 6b); (6) smoke; watch; tag the GitHub deployment `prod`; (7) add the tag `v<version>` to the same digest in the prod registry, create the git tag and GitHub release, publish the API client `<version>`. Prod never builds; every prod task definition comes from this workflow, except `db-bootstrap` and `db-rotate`, which `ci-apply` registers from the same promoted digest.

### UC-DEL-004: Hotfix (DP2)
The flow is `foundation-playbook.md` §5.6. Apps: the founder creates `hotfix/<topic>` from `release`; its pushes deploy to preprod (environment `preprod` admits `dev` and `hotfix/*`) under the release lock with the `preprod-frozen` flag, so `dev`'s preprod deploys wait; a pull request into `release` with the founder's approval promotes that digest; `release` merges back into `dev` at once (merge commit), which redeploys `dev` to preprod and clears the flag. Infra: proven in the sandbox, applied to prod from the approved pull request, never applied to preprod from the hotfix branch.

### UC-DEL-005: Release the web app (`onepeek-web`)
Same shared workflow with `image: web`, no migrate, plus an `assets` job between `sbom-sign` and `rollout`: extract `/app/dist/assets` from the built image (so the files are the exact bytes in the image), `aws s3 sync` to `web-assets/sha-<12>/` with `Cache-Control: public, max-age=31536000, immutable`, never overwriting. The new `web` replicas render HTML that points at `/assets/sha-<12>/` (the image's `RELEASE` is its commit, so prod serves the same folder name); old replicas keep pointing at the old folder, which still exists, so a rollout never breaks a loaded page. The pipeline then deletes asset folders that are both beyond the last 10 releases and older than 90 days.

**Web asset path (one definition, owned by `infra/delivery-pipelines.md`):** `https://<domain>/assets/<release>/…`, same origin. `web` serves `/assets/<release>/` from its image and, on a miss (an old page during a rollout), from the `web-assets` bucket prefix `<release>/`; Cloudflare caches `/assets/*` for a year (immutable). The pipeline copies each release's files to `web-assets/<release>/` before rollout and keeps the last 10 releases (and anything younger than 90 days). The setting is `WEB_ASSETS_BASE_URL` (`https://<domain>/assets`). Smoke: `/`, a public profile page, and the `web` version via ECS (its `/health` is not routed from the edge). Promotion copies the folder to the prod bucket before the rollout.

### UC-DEL-008: Release the MCP Gateway (`mcp-athena`, decision 130)
Same shared workflow with `image: mcp`, no migrate and no assets: build, scan, SBOM, sign, register the `onepeek-<env>-mcp` family and roll out the one `mcp` service, then watch. Smoke: an unauthenticated `POST /mcp` `initialize` through the edge returns the bearer challenge, and the `mcp` version via ECS. Promotion and hotfix follow UC-DEL-003 and UC-DEL-004 (build once, promote by digest). The gateway calls only versioned internal front doors (`/internal/v1`), so a backend release and an `mcp` release ship independently; a tool needing a new front-door method ships after the backend release that adds it.

### UC-DEL-006: Publish the design system (`onepeek-design-system`)
Changesets. Every pull request into `dev` that changes a package needs a changeset (CI check `changeset-check.yml`). **On every push to `dev`** (`prerelease.yml`): test, build, then publish a snapshot `x.y.z-next.<datetime>` under the `next` dist-tag; nothing is committed back (`design-system.md` §9). **On `release`** (`release.yml`): `changesets/action` keeps a "Version packages" pull request open; merging it bumps versions and changelogs, then build, test, `changeset publish` to GitHub Packages (`@onepeek/*`) under `latest`, tag. Nothing is deployed and no cloud role is used; Dependabot opens update pull requests in `onepeek-web` and the extension.

### UC-DEL-009: Cancel a release (foundation reset W2.7; provisional, 2026-11-05, revised after review rounds 1 and 2)
`cancel-release.yml` is a reusable workflow in `OnePeek/.github`, called by a thin `workflow_dispatch` caller in `onepeek-infra`, `backend-service`, `onepeek-web` and `mcp-athena`. Why it lives there, who may run it and what that does and does not guarantee on GitHub Free are in `foundation-playbook.md` §5.4a. The caller's job grants `actions: write` (to cancel its own repo's run), `contents: read`, `id-token: write` and `issues: write` (the put-back opens an issue, as row 9 does; provisional, 2026-11-05), and passes the agents' App secrets. The reusable workflow's jobs run in `concurrency: cancel-release-<env>-<scope>` with `cancel-in-progress: false`. It is dispatched on `release`, the ref the preprod deploy roles trust until launch (§7).

| Input | Type | Values |
|---|---|---|
| `environment` | choice | `preprod`, `prod` (prod: the founder only; for agents enforced by the operator tool `.github/scripts/cancel_release.py` (decision 175) and the P19 hook, because agents dispatch with the founder's own login, `foundation-playbook.md` §5.4a option A) |
| `reason` | string, required | Written to the run summary and to the issue a put-back opens |

The scope is the caller's own: infra `infra`; backend `backend`; web `web`; MCP `mcp`. The role is the repo's deploy role for an app, and `onepeek-<env>-cancel-infra` (lock grants only) for infra, never `ci-apply` (§7).

1. **`authorise`** (no `id-token`):
   - Mint the App token (Actions read; Contents read on `onepeek-infra`, to read `policy/approvers.yaml` at `release`). Refuse unless the token step's `app-slug` output equals `agents_app` in that file.
   - Both `github.actor` and `github.triggering_actor` must be the founder (`founder` in that file), in both environments. There is no `<agents_app>[bot]` branch: under option A the App never holds Actions write, so agents dispatch through `cancel_release.py` with the founder's login, and this check cannot tell them apart (`foundation-playbook.md` §5.4a; provisional, 2026-11-05, review round 2).
   - Anyone else is refused before any credential exists.
2. **`cancel`** (needs `authorise`): check both actors again, then assume the role. Print the `lock-status` fields of every key (never the token), then read the keys this caller may touch: for an app, `locks/<scope>.json`; for infra, every key whose record names infra's run.
   - **Absent:** report "lock free, nothing held" and end green.
   - **The record names another repo:** refuse, naming that repo (for an app key held by infra's release: "cancel from `onepeek-infra`").
   - **The holder's run has finished:**
     - `locked` or `done`: remove the key with the conditional delete (the stale rule).
     - `migrating`: find the task (`migrate_task`, or with no ARN `ecs list-tasks --cluster onepeek-<env> --started-by <run_id>-<run_attempt>` with no other filter, then `ecs describe-tasks` to keep only the `onepeek-<env>-migrate` family; a stopped task stays visible only about 1 hour, `foundation-playbook.md` §5.4a "Stale keys"). While it is not `STOPPED`, wait up to 15 minutes (the migrate step's limit); still running: fail naming the task and keep the key. `STOPPED`, or never started: remove the key.
     - `rolling` (the repair, E11), exclusive:
       1. claim the record: write it with `repair_run` (this run) and a new `repair_token`, still `rolling`, with `If-Match` on the ETag read. Lost (412, or 409 then a changed ETag): stop, naming the other repairer. A record naming a live `repair_run`: stop without writing;
       2. put every service in `previous` back, then `services-stable` (20 minutes), the sandbox aliases back to `previous_lambda`, and an issue as in row 9;
       3. delete the key with `If-Match` on the claim's ETag. If step 2 failed, keep the key and fail.
   - **The holder's run is live:**
     - For `infra`, while the holder's `apply` job is running, refuse: an apply is never cancelled (`foundation-playbook.md` F27). Run it again after the apply.
     - Otherwise `POST /repos/<repo>/actions/runs/<id>/cancel`, never `force-cancel`. Then poll the key every 15 s for up to 75 minutes (`finish`'s limit of 60 plus 15 for its runner; the `cancel` job runs on `stateful` with a wait cap of 95 and `timeout-minutes: 110`, and re-mints its App token and role every 50 minutes, `foundation-playbook.md` §5.4a "Waits that fit the runners"):
       - the key is gone: done;
       - the key names another run: report "freed by <run>, now held by <other run>" and end without touching it;
       - the run finished but the key is still there: take the "run has finished" branch above;
       - the time is up: fail with `waiting for <repo> (<scope>, run <id>); re-run`, adding the phase, and remove nothing.
3. **Report** (the run summary and the log):
   - "lock free", or why not;
   - the holder's run link, commit and conclusion;
   - the phase at the cancel;
   - for `rolling`, each service with its revision before and after (from the last record read, then `ecs describe-services`), and the sandbox aliases;
   - for `migrating`, the migrate task's exit code, or the task still running.

**Never:**
- remove a key held by a live run without cancelling that run first;
- force-cancel;
- stop a migrate task, or remove a `migrating` key while its task is not `STOPPED`;
- write a record it has not claimed;
- cancel a run that waits for a key without holding one (cancelling that by hand is harmless: it holds nothing).

## 4. Edge cases and failure modes
| # | Situation | Behaviour |
|---|---|---|
| E1 | Migration fails | The release stops before any service changes; nothing is tagged |
| E2 | One service never becomes healthy | Circuit breaker rolls that service back; the job fails; **all** services are rolled back to the recorded revisions so versions stay aligned (DA1). If `verify`'s rollback does not run or fails (runner killed, cancel), the record is still `rolling` and `finish` puts them back; if that fails too, the key stays `rolling` (E11) (`foundation-playbook.md` §5.4a) |
| E3 | Alarm in the 10-minute watch | Step 9 rolls back every service; the release is marked failed; an issue is opened with the alarm names. A failed rollback leaves the record `rolling`, so `finish` tries the put-back again and unlocks only if it succeeds; otherwise E11 |
| E4 | Signature missing or from another key | Deploy refuses (§5); no task definition is registered |
| E5 | Two releases at once, in one repo or across repos | One lock key per scope (`foundation-playbook.md` §5.4a): two releases of one scope serialise (the second waits up to 30 minutes); two scopes with no edge between them run in parallel; an infra release takes every key, try-or-release, so it never runs beside an app release, and no app release starts while an infra release is queued or running. A key whose run has finished is taken over, unless its phase is `rolling` (E11) or its migrate task has not stopped |
| E10 | A release is cancelled (`cancel-release.yml`, UC-DEL-009, or by hand), or a runner is killed | `finish` acts on the lock record's phase, never on `cancelled()`: `locked` or `done`, nothing to undo; `migrating`, the task is waited for (15 minutes), never stopped and never rolled back (expand/contract), and the key is kept while it runs; `rolling`, every service goes back to `previous`. It unlocks only when nothing is left to undo or the put-back succeeded (`foundation-playbook.md` §5.4a) |
| E11 | A run ended while its key was `rolling` (its `finish` lost, a force cancel, or a put-back that failed) | Nobody takes the key over and nothing deploys in that scope; every take names the run and `cancel-release.yml`, which claims the record (one repairer only), puts the services back and frees the key (UC-DEL-009) |
| E6 | Rollback target's schema was contracted | The N-1 test made this impossible within one version; older targets need the founder's approval in `reason` and run the target's N-1 report |
| E7 | The services file names a service the image cannot run | The `rollout` job validates the file against the image's `app-run --list` before step 6 |
| E8 | Infra plan artifact expired or missing | Apply stops; recovery is `replan.yml` (`foundation-playbook.md` §5.1 step 7a) |
| E9 | Runner lost mid-rollout | ECS finishes or rolls back on its own; the re-run is idempotent (registers the same revision, `update-service` is a no-op) |

**Caller shape** (`backend-service/.github/workflows/release.yml`; the repo only passes inputs):
```yaml

on:
  push: { branches: [dev] }       # preprod; prod is promote.yml on release
permissions: { contents: read }
jobs:
  release:
    permissions: { contents: write, id-token: write, packages: write, deployments: write, issues: write }
    uses: OnePeek/.github/.github/workflows/release-ecs.yml@<sha>   # pinned
    with:
      environment: preprod
      image: backend
      extra-images: sandbox
      migrate: true
      assets: false

      role-to-assume: ${{ vars.AWS_ROLE_PREPROD }}
      signing-key: awskms:///alias/onepeek-preprod-image-signing
```
Inside `release-ecs.yml`, every job sets `permissions:` to the minimum its steps need and a job `timeout-minutes`; the steps keep their own `timeout-minutes` (build 20, migrate 15, rollout 20, watch 12), and `aws-actions/configure-aws-credentials` with `role-session-name: <repo>-<run id>` so CloudTrail ties every AWS call to a run. The jobs that wait (`prepare`, `finish`, and `operate.yml`'s `lock` and the job that runs its `finish` logic) run on the `stateful` class with the caps and job limits of `foundation-playbook.md` §5.4a "Waits that fit the runners" (`prepare` 135, `finish` 60, each a named `TIMEOUT_EXCEPTIONS` entry), re-mint their App token and role every 50 minutes inside a wait, and fail at a cap with `waiting for <holder> (<scope>, run <id>); re-run` (provisional, 2026-11-05).

**Rendering a task definition** (one function, used by release, operate, promote and by `ci-apply` for `db-bootstrap` and `db-rotate`):
1. `template = s3.get("s3://onepeek-<env>-deploy/taskdef/<service>.json")` (JSON written by Terraform, with no image field).
2. Set `image` to `<registry>/<image>@sha256:<digest>` in every container whose `image` is missing, null or empty (a daemon's sidecar); refuse a result where any container still has no image.
3. Add the tags `commit=sha-<12>` and `release-run=<run id>`; add `version=<semver>` only on promotion.
4. **Drop protection, per service (not for one-offs):** compare the setting names and secret names of the new revision with those of the service's currently registered task definition. Refuse the render if a name has disappeared, unless it is listed in the caller's reviewed `allow-drop` input (the contract step of an expand/contract change). Also refuse a name that appears in both settings and secrets. The refusal is also per service (provisional, 2026-11-05): one name may not be a setting in one container of the task definition and a secret in another, and drop protection compares the union of names over all containers of the task definition (`OnePeek/.github#51` implements this).
5. `register-task-definition`; record the previous revision of the service for rollback.

**Follow-ups (not part of this change):**
- Checking the digests of running tasks, not only the service's task definition, needs `ecs:ListTasks` on the deploy role (granted with W2.7, §7): a later change in the shared workflows.
- infra's `db-bootstrap.yml` renames its `version` input and tag to `commit`.
- Callers move to push-on-`dev` only after the cross-repo release lock exists and the preprod role trusts include `ref:refs/heads/dev`; `operate.yml` runs from `dev` for preprod at the same time.

**Signature verification** (every deploy, rollback and promotion): `cosign verify --experimental-oci11 --insecure-ignore-tlog=true --key <key> <registry>@<digest>`. **Attestations** (the SBOM; the promotion attestation at launch) are Sigstore bundles and are verified with `cosign verify-attestation --new-bundle-format --insecure-ignore-tlog=true --key <key> --type <type> <registry>@<digest>`; whether that needs a pinned `--trusted-root` file or the public Sigstore TUF root is settled in experiment X-COSIGN before the first `verify-attestation` is built (none runs today). There is **one signing key, in preprod only** (`alias/onepeek-preprod-image-signing`): images are built and signed once. Preprod verifies with the KMS key; prod verifies the **same preprod signature** with that key's exported public key (non-secret setting `/onepeek/prod/release/signing_public_key`), so prod has no signing key and never re-signs. Promotion adds a **prod attestation** (`cosign attest --type https://onepeek.info/attestations/promotion/v1`, signed with the prod-account KMS key `alias/onepeek-prod-promotion` (defined in `aws-stack.md` §8.8; `kms:Sign` only for `onepeek-prod-deploy-backend-service` and `onepeek-prod-deploy-onepeek-web`, §7 and the access matrix in `aws-stack.md` §12)) recording who approved, when, and the preprod watch result; prod deploys require both the build signature and the promotion attestation. A deploy references images **by digest only**; the deploy roles can register only task definitions in their own families (§7), so the pipeline is the only path to a running image.

### 6.2 Image tags (DP4)
`sha-<12 hex>` on every build (preprod), plus `v<version>` added to the same digest in the prod registry on promotion; both immutable (ECR `IMMUTABLE`). Cosign signatures and attestations are OCI referrers of the image digest (no `sha256-*.sig` tags). **Fallback** if referrers misbehave in experiment **X-COSIGN** (`../README.md`): ECR `IMMUTABLE_WITH_EXCLUSION` with an exclusion filter for tags starting `sha256-`, and cosign's default tag scheme. The ECR lifecycle keeps the last 30 `sha-*` deployments in preprod and the last 30 version tags in prod and every referrer of a kept image, and expires untagged images after 7 days (referrers are kept while their subject exists).

### 6.3 Registries
One ECR per account (`backend`, `sandbox`, `web`, `mcp`, `gateway`, `egress-proxy`). Promotion copies by digest into prod; prod never pulls from the preprod account at runtime. TRD §7.4's `shared/` folder is therefore not created.

### 6.4 Versions (DP4)
release-please (manifest mode) runs on `dev` and keeps one open "release v<next>" pull request with the changelog and the manifest bump, computed from Conventional Commit titles. Merging it into `dev` marks the version; the next promotion (`dev` → `release`) tags it. Preprod deploys carry only the commit. Before launch versions stay `0.x`.

- **Hotfix pull requests** (`hotfix/*` into `release`) check the other repos at `release`; every other pull request into `release` checks them at the head of their open `dev` → `release` pull request, else at `release` (fail closed when that cannot be read). The `hotfix/*` name is trusted once the creation ruleset of `foundation-playbook.md` §5.7 exists.

### 6.4a Every caller passes every required input (F35, T-46; provisional, 2026-11-06)
- **Why.** Since `.github` v1.16.0, `release-lock.yml` requires `scope`. The infra `release.yml` and `replan-apply.yml` never passed it. No release ran, so nobody saw it, and the first release would have been refused. GitHub reports a missing required input only when the call runs, and a release path runs rarely.
- **The check.** `scripts/check_caller_inputs.py <repo-dir> --shared <.github checkout>` in `OnePeek/.github`:
  - It finds every `uses: OnePeek/.github/.github/workflows/<file>@<sha>` in the caller's `.github/workflows/*.yml` and `*.yaml` (GitHub accepts both).
  - It reads `<file>` at that commit (`git show <sha>:<path>` in the `.github` checkout; a commit it cannot find is a failure, never a skip).
  - It fails when a call's `with:` lacks an `on.workflow_call.inputs` entry that has `required: true`. It also fails on a `with:` key the called workflow does not declare, and a `secrets:` name the callee marks `required: true` but the call neither passes nor covers with `secrets: inherit`.
  - The same applies to a local reusable call (`uses: ./.github/workflows/<file>`), read from the caller's own tree.
  - Each failure is one line: `<caller file>:<line>: <job> calls <file>@<tag> without required input <name>` (or `unknown input`, `required secret`). The exit code is 1 on any failure.
- **Where it runs.**
  - In `pins.yml`, which every repo calls, on every pull request. That workflow already checks out `.github` at the caller's pin into `_shared`. Inside `.github` itself the check uses `--shared .`.
  - On the laptop, `vanguard local-ci` runs it directly in `shared_checks()`, as it runs the runner-label lint: `check_caller_inputs.py <repo> --shared $ONEPEEK_WORKSPACE/.github`. The step in `pins.yml` cannot run locally, because it needs the CI-only pin SHA.
  - It replaces no existing check.
  - **PyYAML on our runner** (T-46 gap, 2026-11-06, provisional): the onepeek runner image has no pip and no PyYAML. So the step first runs `python3 -m venv "$RUNNER_TEMP/cci" && "$RUNNER_TEMP/cci/bin/pip" install --quiet pyyaml==6.0.3`, the same pin as `workflow-lint.yml`, and calls the script with that venv's python. The runners already reach PyPI for `uv` (backend checks). The step goes after the `_shared` checkout and before the final `--docs auto` step.
- **Rulings (T-46 gap check, 2026-11-06, provisional):**
  - **`<tag>`:** the trailing `# vX.Y.Z` comment on the `uses:` line, or else the first 12 hex digits of the commit. A local call prints `./.github/workflows/<file>` with no `@`.
  - **Required wins.** An input with `required: true` must be passed even when it has a `default:` (fail closed). An input without `required: true` is never flagged.
  - **Unknown secret:** a `secrets:` name the callee does not declare is a failure (`unknown secret <name>`), as GitHub refuses it too.
  - **The fail-closed failures,** in the same `<caller>:<line>: <job> calls <file>@<tag>: <reason>` shape, with these reasons:
    - `pin commit not found`;
    - `file not found` (a local callee too);
    - `cannot parse` (the caller or the callee);
    - `not a reusable workflow` (no `on.workflow_call`);
    - `ref is not a commit sha` (an `OnePeek/.github` ref that is not 40 hex). `check_pins` refuses it as well, so both checks report it.
- **Tests:** a missing required input, an unknown input, a required secret missing and covered by `inherit`, a default making an input optional, a pin commit not found, a local call, and the live infra workflows passing after infra #179.

### 6.5 The other repos' ref: one script for every cross-repo check (follow-up of 2026-11-06; provisional, 2026-11-06)

**What.** The rule "which version of another repo does this pull request check against" lives in one script, `OnePeek/.github` `scripts/peer_ref.py`, reached through one composite action, `OnePeek/.github/actions/peer-ref`. `contract.yml`, the backend and web boot checks (`image-smoke.yml`, `image.yml`) and web `e2e.yml` all use it.

Web `e2e.yml` already disagrees: on a release pull request it checks `backend-service` out at `github.base_ref`, that is `release`, not at the release candidate. Three copies of one rule drift.

| The pull request | The other repo's ref |
|---|---|

## 8. Merging and the release path (branching-and-delivery §2)
A change merges into `dev` only with every required check green (founder, 2026-11-03), so the release path may assume the pull request's checks passed. Security gates in the release itself (Trivy critical, signature, plan match) still block on their own.
- If a heavy suite that runs only on promotion (N-1 against the prod-live version, end-to-end) fails, the workflow opens an issue tagged `release-blocker` on that version; `promote.yml` refuses a version with an open `release-blocker`.
- The destructive-plan stop stays at all times.

### 8.1 Release pull requests run only release-specific checks (foundation reset W2.2; provisional, 2026-11-06)

**What.** A `dev` → `release` pull request (a *promotion pull request*) runs only the checks whose result can differ from what `dev` already proved. Every other check is replaced by one new required check, `release-gate`, which proves that the tree the promotion ships is the tree of a `dev` commit whose full CI was green, and refuses otherwise. Target: the promotion pull request is green in 5 minutes or less.

**Why.** On 2026-11-05 a release pull request re-ran unit, end-to-end and lint on a tree `dev` had already tested, 10 to 20 minutes each time. A promotion merges with a merge commit (`branching-and-delivery.md` §2), and after a hotfix `release` is merged back into `dev` at once, so the promotion's tree is normally exactly `dev`'s head. Re-testing the same tree proves nothing new.

**A gap this closes first.** Today a pull request into `dev` runs only the fast tier, and a push to `dev` runs only the pin check. The full suite and the coverage gate run only on release pull requests and nightly (decision 152). So "the tree equals `dev`, which already passed" is not true yet: no `dev` commit has a full green run. The design therefore adds **certification**: the full tier runs on every push to `dev` (founder question FQ-W2.2, below).

#### Which checks are which

The rule: a check is **release-specific** when its result depends on something other than the tree: the `release` branch (what prod runs), another repo's release candidate, or live environment state. It is **tree-only** when only the tree decides it. Tree-only checks run in certification and are skipped on a promotion pull request; release-specific checks run on the promotion pull request as today.

| Repo | Release-specific: run on the promotion pull request | Tree-only: skipped there, run in certification on the push to `dev` |
|---|---|---|
| every repo with a `release` branch (`backend-service`, `onepeek-web`, `onepeek-infra` today; `mcp-athena` when it releases) | `depends-on`, `pins` (the docs pin is on docs `dev`), `release-gate` (new), `contract` (the other repos at their release candidates, §6.5); and, once a caller has moved to it, `fast` (the merged job of §9.1: it runs on a promotion pull request, and its `secrets` step is the only tree-only part) (orchestrator, provisional, 2026-11-10) | `secrets` (gitleaks; inside `fast`, a step) |
| `backend-service` | a new job `release-checks`: `oasdiff` against `release` (every breaking change since prod, not since the last `dev` commit) and, once built, the N-1 migration test against the prod-live revision; the boot check against `onepeek-infra`'s release-candidate `rendered/taskdef.*` (`image-smoke.yml`, the build hits the layer cache that the `dev` push filled) | `python` (ruff, pyright, unit, the full suite, coverage), `architecture` (types, boundary checks, OpenAPI up to date, services-file validation, squawk on new revisions, the traced suite), `api-client` (its build and tests) |
| `onepeek-web` | `no-prerelease-deps` (promotion mode refuses every prerelease of `@onepeek/*`); the boot check against `onepeek-infra`'s release-candidate rendered environment (`image.yml`); `e2e` against `backend-service`'s release candidate (§6.5; today it wrongly uses `release`) | `node` (lint, types, the full unit suite) |
| `onepeek-infra` | `plan` and `preprod-in-sync`; `ci-runners` (the privileged fleet plan runs only on promotion, playbook §8a S1) | `terraform` (fmt, validate, tflint, `terraform test`), `static` (one job since PIPE-SIMPLE item 2, F415: its steps were the jobs `skeleton-image`, `collector-config`, `deploy-filters`, `rendered` and `layout`), the tree-only tests in `org.yml` and `security.yml` (their plans, if any, stay) |

A `hotfix/*` pull request into `release` is **not** a promotion pull request: it runs every check, as `foundation-playbook.md` §5.6 step 2 says, because its tree was never on `dev`.

**How a tree-only job is skipped.** Each tree-only job in the caller workflows gets the condition `!(github.event_name == 'pull_request' && github.base_ref == 'release' && github.head_ref == 'dev')`, joined with `&&` to its existing `if`. A skipped job reports `skipped`, which `ship_change_set.py` and GitHub both treat as passed; `release-gate` is the check that makes skipping safe. **The merged `fast` job is classed release-specific** (R-S2i-6, (orchestrator, provisional, 2026-11-10)): it always runs on a promotion pull request, so `pins`, `contract` and `no-prerelease-deps` run there as before. Its `secrets` step is the only tree-only part and carries `if: always() && !(github.event_name == 'pull_request' && github.base_ref == 'release' && github.head_ref == 'dev')` (the canonical condition above joined to `always()`, so an earlier failed step never skips the scan); that step is skipped on a promotion pull request and runs in certification. `fast` is in `certified.needs`, so the scan stays part of certification. Where a release-specific step sits inside a tree-only job today (backend `oasdiff` in `architecture`), it moves to the backend's new `release-checks` job.

#### Certification (the push to `dev`)

- `checks.yml` on `push` to `dev` runs every tree-only job in **full mode** (the full suite and the coverage gate, `full: true`, no "affected only" selection, no path filter inside a job). A push to `release` still runs only the pin check.
- A final job `certified` `needs:` every tree-only job (and `fast`, once a caller has moved to it), runs with `if: ${{ always() && github.ref == 'refs/heads/dev' && (github.event_name == 'push' || github.event_name == 'workflow_dispatch') }}`, and fails unless every needed job's result is `success`. It runs only for certification events (a push to `dev`, or a manual `workflow_dispatch` run on `dev`); on a pull request (a promotion included), a push to `release` or a nightly run it is skipped, which counts as passed, so it never turns those runs red. `always()` is kept because a job whose `needs` were skipped or failed would otherwise be skipped itself, and a skipped `certified` on `dev` would certify by omission (GitHub runs an `always()` job even when its dependencies were skipped). A tree-only job that is `skipped` on a push therefore fails certification; nothing is certified by omission.
- The image workflow (`image-smoke.yml` in backend, `image.yml` in web) already builds on a push to `dev`; its run is part of certification.
- `concurrency` cancels a superseded run only for a `pull_request` (`cancel-in-progress: ${{ github.event_name == 'pull_request' }}`, §9.1), never for a push to `dev`: a running push to `dev` is never cancelled; a pending one can be replaced by a newer push, because a concurrency group keeps only one pending run (edge case below). This replaces the earlier "cancel the superseded push to `dev`" rule, because decision 180 (founder, 2026-11-08) is newer (orchestrator, provisional, 2026-11-10).

#### The gate: `release-gate` (`OnePeek/.github` `scripts/release_gate.py` and the reusable `release-gate.yml`)

Inputs: the repo, the pull request number, the list of certifying workflow files (`checks.yml`, plus `image-smoke.yml` or `image.yml`). Token: the job's own `GITHUB_TOKEN` with `contents: read`, `actions: read` and `pull-requests: read` on the calling repo only (no App token, nothing in another repo). Class `light`, `timeout-minutes: 30`.

1. **Shape.** Read the pull request. Refuse unless its base is `release`, its head ref is `dev` and its head repo is this repo. Otherwise (a `hotfix/*` head) pass with "not a promotion: every check runs" and do nothing more. Any other head into `release` is refused: only `dev` and `hotfix/*` may target `release` (`branching-and-delivery.md` §1).
2. **What ships.** Fetch `release` and the head `H` (`fetch-depth: 0` on those two refs only). Compute the merge result's tree `T = git merge-tree --write-tree origin/release H` (Git 2.38 or later; the runner image has it). A conflict refuses ("the promotion conflicts with `release`"). This is the tree the merge commit will hold, the same tree GitHub's test merge ref holds.
3. **Tree equals `dev`.** Refuse unless `T` equals `H^{tree}`. When they differ, `release` holds a change `dev` lacks (a hotfix not merged back): the message lists `git log --no-merges --format='%h %s' H..origin/release` and says "merge `release` back into `dev` first (playbook §5.6)". Trees are compared, never commit SHAs, because `release` carries merge commits `dev` lacks while their trees match.
4. **A green certification for that tree.** Walk `dev`'s first-parent history from `H`, at most 20 commits, and keep the commits `C` with `C^{tree} == T` (normally only `H`; an empty back-merge commit is another). For each, newest first, read the runs of each certifying workflow with `GET /repos/<repo>/actions/workflows/<file>/runs?head_sha=<C>&branch=dev`, keeping only `event` `push` or `workflow_dispatch`. A workflow counts as green for `C` when its newest run there has `status: completed` and `conclusion: success`, and, for `checks.yml`, its `certified` job (from the run's jobs, `filter=latest`) concluded `success`. The newest run's conclusion already reflects its latest attempt. `C` is certified when every certifying workflow is green for it.
5. **Waiting.** When the newest run for `H` is queued or in progress, poll every 30 s up to 25 minutes, then fail with `certification of <sha7> still running; re-run` (the merge tool re-runs it). When it ended `failure` or `cancelled`, or no run exists for `H`, the gate first checks every other eligible `dev` commit whose tree equals `H^{tree}` (newest first), and passes on the first green certification among them; only when none is green or still running does it refuse: `dev <sha7> has no green certification (<run link> <conclusion>): fix dev or re-run its checks`. Certification normally finishes long before anyone opens the promotion, so the gate takes about a minute.
6. **Summary.** The step summary names `H`, `T`, the certified commit and each run used.

**The merge tool re-checks at merge time.** A promotion pull request gets no new run when only `release` moves (a hotfix merged after the gate passed). The merge tool (`vanguard ship`), before it merges a promotion pull request, calls `release_gate.decide()` itself (the same function, through `gh`) and refuses unless it passes for the current `release` head; it also refuses when `tested_bases()` shows the gate ran against an older `release` head.

**release-please, explicitly.** The release-please pull request (`chore: release v<next>`) merges into `dev` like any other pull request, so its version, manifest and changelog commit is a `dev` commit and is certified by its push like any other; it gets no special treatment and no exemption. The release-please workflow writes only its own pull request branch, never `dev` or `release`; the version tag and GitHub release are made by the release run and are tags, not commits, so `release` never holds a release-please commit `dev` lacks. A pull request opened with `GITHUB_TOKEN` starts no workflow on it (GitHub's rule against recursive runs), which would leave the release-please pull request without its required checks. So the release-please workflow in each repo mints a short-lived `onepeek-ci-bump` App token (installed on all eight repos, decision 168; Contents and Pull requests write, scoped to that one repo) and passes it as the release-please action's `token`; a pull request opened with an installation token does start its pull-request workflows, so it gets every required check before merge like any other pull request, and the merge tool waits on them. The push to `dev` when it merges then certifies it too. If the release-please pull request is still open at promotion time, the promotion ships without the version bump; the gate does not care.

**Edge cases.**
- `dev` moves while the promotion is open: the pull request's head moves with it (its head ref is `dev`), a `synchronize` run starts, and the gate checks the new head, waiting for its certification.
- Certification of the head was cancelled by a newer push: the head is no longer the head; see the line above.
- The nightly full run (`schedule`) runs on `dev`'s head with event `schedule`; it does not count (only `push` and `workflow_dispatch` count, because a scheduled run's commit is whatever `dev` held at that hour and its jobs follow the nightly rules). A person can certify by hand with `workflow_dispatch` on `dev` (event `workflow_dispatch`, `head_branch: dev`), which counts as well (the gate accepts `push` and `workflow_dispatch` events on `dev`).
- A re-run attempt of a certification run that turned green counts (the run's conclusion is its latest attempt's).
- A certified commit whose certifying workflow files were changed by the same commit: the run at `C` used `C`'s own workflow files, so it certified under the rules it ships with. Nothing extra is needed.

**Tests** (`OnePeek/.github` `scripts/test_release_gate.py`, a fake `gh` and real throwaway Git repositories):
- tree of the merge equals `dev`'s head with a green `checks` and image run: passes;
- `release` holds a commit `dev` lacks (an unmerged hotfix): refused, and the message names the commit;
- the merge conflicts: refused;
- `checks` green but `certified` skipped or failed: refused;
- the newest run for `H` failed although an older run for `H` was green: refused (newest wins);
- a run with `event: schedule` or `event: pull_request` for `H` only: refused;
- queued then green within the wait: passes; still running at 25 minutes: fails with the re-run message;
- a `hotfix/*` head: passes as "not a promotion"; a `feat/*` head into `release`: refused;
- two `dev` commits with the same tree, only the older certified: passes on the older one;
- a workflow test: in every caller's `checks.yml`, every job **other than `certified` itself** is either in the release-specific list of this section or carries the skip condition and is in `certified.needs`; the mixed job `fast` is accepted as release-specific when it is also in `certified.needs` and its `secrets` step carries `always() &&` followed by the canonical skip condition (derived from the workflow, so a new job that is neither fails the test); `certified` is the explicit aggregator exception: it is not required to be in the release-specific list, to carry the skip condition or to be in its own `needs`, and a `certified` that lists itself in `needs` fails; the skip condition is the exact canonical string; `certified`'s `if` is the exact canonical certification condition (a `certified` with only `always()` fails);
- a workflow test fixture with a `pull_request` event (a promotion): `certified` is skipped and the run is not red; with `push` to `dev` and with `workflow_dispatch` on `dev`: it runs;
- a workflow test: every caller's release-please workflow passes a `token` from the App mint step, not `GITHUB_TOKEN`; mutation: a release-please step without `token` fails it;
- mutation: comparing commit SHAs instead of trees fails the "merge commits on `release`" test; dropping the `certified` job check fails the "skipped job" test.

**Files to change.** `OnePeek/.github`: `scripts/release_gate.py`, `scripts/test_release_gate.py`, `.github/workflows/release-gate.yml`, `scripts/check_release_skips.py` (the caller workflow test, run by `workflow-lint` against callers in `vanguard local-ci` and by each caller's `pins` job); `OnePeek/vanguard`: `vanguard ship` (the merge-time call, decision 175). `backend-service`, `onepeek-web`, `onepeek-infra` (and `mcp-athena` when it releases): `checks.yml` (the skip condition, push-to-`dev` full mode, `certified`, the `release-gate` job, backend `release-checks`), `image-smoke.yml` / `image.yml` (the boot check reads the release candidate through §6.5).

### 9.1 Pipeline rules of the stabilization (decision 180, founder 2026-11-08)

### 15.1 Workflow tests for the GitHub semantics we rely on (foundation reset W6.3; provisional, 2026-11-06)

**What.** Our workflows depend on how GitHub evaluates `if:`, `needs` and re-runs. Today one test encodes part of that for one workflow; the rest is assumed. Lesson R1 of 2026-11-05 was that tests encoding our assumptions passed while the platform behaved otherwise. So the semantics get (1) one shared model, (2) a probe that records what GitHub really does, and (3) tests that run every release-path workflow through the model.

**What exists.** `scripts/test_release_ecs.py` `SkippedBuildBranch` checks that every job below the split build in `release-ecs.yml` calls a status function (the skipped-ancestor rule), and `JobGraph._simulate` evaluates `needs` and `if` for that file only. `scripts/test_release_lock.py` `PartialReRun` checks the lock-attempt guard text and that `db-bootstrap` is skipped outside the locking attempt. After `.github` #54 (13f5de9) the lock record carries `run_id` and `run_attempt`, a take by a later attempt of the same run takes over, and `finish` acts by phase.

**The semantics, each as a rule the model implements.**
1. **Implicit `success()`.** A job `if:` with no status function means `success() && (...)`; with no `if:` at all, `success()`. `success()` at job level is false when any job in its `needs` closure (transitively) is not `success`, so a skipped ancestor skips the job (skipped-ancestor propagation).
2. **Status functions at job level.** `always()` is true even after a cancel; `!cancelled()` is false after a cancel; `failure()` is true when any job in the transitive `needs` closure failed; `cancelled()` is true after a cancel. A job's `needs.<id>.result` is `success`, `failure`, `cancelled` or `skipped`; a skipped job's outputs are empty strings.
3. **After a cancel.** Jobs already running get the cancel signal and their steps with `always()` still run; jobs not yet started start only when their `if` holds with `cancelled()` true (so `always()` jobs start, `!cancelled()` and implicit-success jobs do not).
4. **Step level.** A step's status functions refer to the steps before it in the same job; `steps.<id>.outcome` is before `continue-on-error`, `conclusion` after.
5. **YAML.** An `if:` that begins with `!` must be written inside `${{ }}` (a bare `!` is a YAML tag).
6. **Re-run failed jobs.** It re-runs the failed and cancelled jobs and every job that depends on them, transitively; jobs that succeeded are not re-run and their outputs from the earlier attempt are what `needs.<id>.outputs` returns; `github.run_id` stays and `github.run_attempt` rises by one for the whole run; the OIDC token of the new attempt carries the new `run_attempt`. "Re-run all jobs" re-runs every job.
7. **Concurrency.** A run joining a `concurrency` group with `cancel-in-progress: true` cancels the group's running run, and a re-run attempt joins the group again (this is why W2.6 must never re-run a superseded run, `ci-runners.md` §4.1).
8. **Reusable workflows.** Inside a called workflow, `job.workflow_sha` (the `job` context property, documented as "the commit SHA of the workflow file that defines the current job"; `job_workflow_sha` is only the name of an OIDC claim, and `github.job_workflow_sha` is not a context property) is the commit the called workflow was loaded from (the pin), not the caller's commit. The probe proves it; until then, every use refuses an empty or malformed value.

**(1) The model.** `OnePeek/.github` `scripts/workflow_model.py` (standard library plus PyYAML) loads a workflow, evaluates each job's `if` and `needs` under rules 1 to 3 and 6 for a given scenario (each job's result, a cancel at a given job, a re-run of failed jobs or of all jobs with the previous attempt's results and outputs), and returns which jobs run and the `needs` values each sees. It replaces `JobGraph._simulate`. Expressions it cannot evaluate fail the test, never pass silently.

**(2) The probe.** `OnePeek/.github` `.github/workflows/semantics-probe.yml` (`workflow_dispatch` only, GitHub-hosted, public repo, no secrets, no permissions beyond `contents: read`) is a small graph built to exercise rules 1, 2, 3 and 6: a skipped job with dependants using each status function, a failing job, a job that fails only on attempt 1 (`github.run_attempt == 1`) with an output read below it, and a cancel step that cancels its own run through `GITHUB_TOKEN` (needs `actions: write` on that one job). It also calls a small reusable workflow of its own and records `job.workflow_sha` there, which `foundation-playbook.md` §5.4a relies on for the `_gh/` checkout ("Freeze and thaw"); rule 8 below. A script `scripts/record_probe.py` reads the finished run's jobs (each attempt) and writes `scripts/testdata/github_semantics.json`: the run link, the date and each job's result per attempt and scenario. It is run by hand once, after a re-run of failed jobs, and again whenever the runner image or GitHub changes these rules; the file is committed.

**(3) The tests.**
- `test_workflow_model.py`: the model, run on the probe workflow's own file, gives exactly the results in `github_semantics.json`. A rule written wrongly in the model fails here, against GitHub's recorded behaviour, not our belief.
- **Skipped-ancestor rule for every release-path workflow**, generalising `SkippedBuildBranch`: for `release-ecs.yml`, `operate.yml`, `release-lock.yml`, `cancel-release.yml` (when built), `release-gate.yml` and the callers' `checks.yml` fixtures, every job listed as "must run when an ancestor is skipped" (a per-workflow list in the test, each job with the ancestors whose skip it must tolerate: `release-ecs.yml` `db-bootstrap`, `deploy`, `verify`, `finish`, and `api-client` only for skips other than `verify`; `operate.yml` `unlock`; `checks.yml` `certified`) runs in the model when one of those ancestors is skipped. A further case proves `api-client` stays skipped when `verify` is skipped, because UC-DEL-001 publishes the client only after `verify` succeeds (review of docs #236); and every other job does not run below a failed `depends-on`.
- **Status functions:** in the model, after a cancel at each job of `release-ecs.yml` in turn, `finish` starts and `verify`'s rollback step runs only with `steps.guard.outcome == 'success'`; no job that changes AWS state other than `finish` starts after the cancel.
- **Re-run behaviour of the lock** (after #54): in the model plus the lock functions run as bash with a fake S3 (the existing harness in `test_release_lock.py`):
  - attempt 1 takes the key and `deploy` fails; "re-run failed jobs": `prepare` is not re-run, `needs.prepare.outputs.attempt` is `1`, `deploy`'s guard fails on attempt 2, `db-bootstrap` is skipped, and `finish` (re-run as a dependant) finds the key already freed by attempt 1's `finish` and changes nothing;
  - the same with attempt 1's `finish` killed (key still `locked` with attempt 1): attempt 2's `finish` matches `run_id` and `run_attempt` 1 from `prepare`'s carried outputs and frees it;
  - "re-run all jobs": attempt 2's `prepare` takes over attempt 1's key (`test_an_earlier_attempt_of_this_run_is_taken_over_without_asking_github`, kept) and the release runs end to end;
  - a key in `rolling` from attempt 1: neither re-run kind takes it over; the take fails naming `cancel-release.yml`.
- **The spot re-run kind for releases:** because a failed-jobs re-run of a release can never deploy (the guard), every caller's `spot-rerun-caller.yml` that lists a workflow calling `release-ecs.yml` or `release-lock.yml` must also list it in `rerun_all_workflows`. Today none does (backend and web list `release`, infra lists `release`, only `sandbox` is re-run whole). A check in `check_runner_labels.py`'s caller pass fails such a caller; the callers are fixed in the same round.
- **YAML rule 5:** the workflow lint fails a bare `if: !...`.

**Files to change.** `OnePeek/.github`: `scripts/workflow_model.py`, `scripts/test_workflow_model.py`, `scripts/record_probe.py`, `scripts/testdata/github_semantics.json`, `.github/workflows/semantics-probe.yml`, `scripts/test_release_ecs.py` (use the model), `scripts/test_release_lock.py` (the re-run scenarios), `scripts/check_runner_labels.py` (the `rerun_all_workflows` rule). Callers: `spot-rerun-caller.yml` in `backend-service`, `onepeek-web`, `onepeek-infra` (`rerun_all_workflows: release`, plus `sandbox` for infra).
